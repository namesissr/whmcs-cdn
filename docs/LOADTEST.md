# آزمون بار نودها (Load test) — CDN پاسارگاد

این سند راهنمای اجرای کیت آزمون بار `tools/loadtest/` (SPEC §16.1) است: آماده‌سازی ماشین کلاینت،
راه‌اندازی origin آزمایشی، اجرای سناریوها، خواندن نتایج و — مهم‌تر از همه — به‌دست‌آوردن عدد درست
`capacity_mbps` برای هر نود و تنظیم fair share. مخاطب: مدیر فنی/اپراتور نودها.

> **هشدار ایمنی.** این ابزار بار واقعی تولید می‌کند. فقط روی **نودی که خودتان مالک و اپراتور آن
> هستید** اجرا شود. ابزار بدون `--target` (یک آدرس IP صریح) اجرا نمی‌شود، نام دامنه را به‌عنوان هدف
> نمی‌پذیرد و در هر اجرا این هشدار را چاپ می‌کند. اجرای آن روی زیرساخت دیگران یا بدون هماهنگی با
> دیتاسنتر ممکن است حمله‌ی DDoS تلقی شود. بخش [۹. نکات ایمنی](#۹-نکات-ایمنی) را حتماً بخوانید.

## ۱. اجزای کیت

| فایل | کار |
|---|---|
| `tools/loadtest/pcdn-loadtest` | ابزار اصلی (اجرای `loadtest.py`) |
| `tools/loadtest/loadtest.py` | سناریوها، آمار، گزارش JSON و خلاصه‌ی فارسی |
| `tools/loadtest/lt_proto.py` | پروتکل‌ها: HTTP/1.1، دست‌دهی و فریم‌بندی WebSocket، HTTP/2 حداقلی با کنترل جریان |
| `tools/loadtest/origin.py` | origin آزمایشی echo/sink برای ws، httpupgrade، xhttp، gRPC/h2 (h2c) و HTTP معمولی |
| `tools/loadtest/tests/` | تست‌های pytest (مستقیم روی origin و — اگر nginx نصب باشد — از طریق یک نود واقعی) |

همه‌چیز فقط با **کتابخانه‌ی استاندارد Python 3.11** کار می‌کند. HTTP/2 (برای gRPC و h2) داخل کیت
پیاده‌سازی شده و به بسته‌ی `h2` نیازی **نیست**. اگر `uvloop` نصب باشد خودکار استفاده می‌شود (اختیاری،
حدود ۲۰ تا ۴۰ درصد کارایی بیشتر کلاینت).

## ۲. چیدمان آزمون

```
 [VM کلاینت] ──(بالا: up)──►  [نود Edge]  ──(up)──►  [VM origin: origin.py]
             ◄─(پایین: down)─              ◄─(echo)──
```

- **کلاینت** روی یک VM جدا اجرا می‌شود؛ هرگز روی خود نود (نتیجه بی‌معنی می‌شود) و نه روی سرور مرکزی.
- **origin** (`origin.py`) ترجیحاً روی VM سوم نزدیک نود (همان دیتاسنتر). هر پیامی که کلاینت می‌فرستد
  عیناً برمی‌گردد، پس برای هر سشن تونل `up ≈ down`.
- ترافیک کارت شبکه‌ی نود در آزمون تونل: `tx ≈ up + down` و `rx ≈ up + down` (نود بایت‌های کلاینت را به
  origin و echo را به کلاینت می‌فرستد). ابزار همین را به‌عنوان «برآورد ترافیک خروجی نود»
  (`node_tx_estimate_mbps`) گزارش می‌کند؛ همان کمیتی که heartbeat با نام `tx_mbps` می‌فرستد و
  shedding/fair share با `capacity_mbps` مقایسه می‌کنند.
- پهنای باند VM کلاینت و VM origin باید **بیشتر** از ظرفیتی باشد که می‌خواهید روی نود ببینید؛ وگرنه
  گلوگاه شما کلاینت است نه نود. برای نودهای ۱۰ گیگابیتی از چند VM کلاینت استفاده و نتایج را `merge` کنید.

## ۳. آماده‌سازی ماشین کلاینت

Ubuntu 22.04/24.04 (Python 3.11 یا جدیدتر):

```bash
# کیت را بیاورید (فقط پوشه‌ی tools/loadtest لازم است)
git clone <repo> pcdn && cd pcdn/tools/loadtest      # یا: scp -r tools/loadtest client:~/
python3 --version                                    # >= 3.11
pip install uvloop                                   # اختیاری

# محدودیت‌های سمت کلاینت (برای هزاران اتصال)
ulimit -n 1048576                                    # ابزار soft را خودش تا hard بالا می‌برد
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65000"
sudo sysctl -w net.ipv4.tcp_tw_reuse=1
sudo sysctl -w net.core.somaxconn=65535
```

- هر پروسه‌ی ابزار از یک هسته‌ی CPU استفاده می‌کند. برای بار بیشتر چند پروسه هم‌زمان اجرا کنید
  (هر کدام با `--out` جدا) و بعد `pcdn-loadtest merge` بزنید (بخش ۶).
- هر آدرس IP کلاینت حداکثر حدود ۶۴ هزار اتصال هم‌زمان به یک `IP:port` نود باز می‌کند (پورت‌های محلی).
  اگر خطای `client_ports` دیدید، VM یا IP کلاینت دیگری اضافه کنید.
- خطای `client_fd_limit` یعنی `ulimit -n` کلاینت کم است؛ هر دو محدودیت **کلاینت** هستند نه نود.

## ۴. origin آزمایشی و سایت آزمایشی روی نود

### ۴.۱ اجرای origin

روی VM origin:

```bash
python3 tools/loadtest/origin.py --port 8080            # پیش‌فرض 0.0.0.0:8080
# گزینه‌ها: --body-size 16384 (اندازه‌ی پیش‌فرض پاسخ GET)  --max-age 3600 (Cache-Control)
#           --tls-cert/--tls-key (فقط برای آزمون مستقیم کلاینت بدون نود)
```

رفتار origin روی یک پورت:

| درخواست | پاسخ |
|---|---|
| `Upgrade: websocket` + `Sec-WebSocket-Key` | WebSocket echo (مسیر `ws`) |
| هر `Upgrade:` دیگر | 101 و echo خام بایت‌ها (مسیر `httpupgrade`) |
| هدر `X-PCDN-LT: xhttp*` | XHTTP: `GET <base>/<sid>` دانلود chunked، `POST <base>/<sid>/<seq>` (packet-up) یا `POST <base>/<sid>` chunked (stream-up)؛ آپلودها روی همان سشن echo می‌شوند |
| HTTP/2 بدون TLS (h2c، همان چیزی که `grpc_pass` نود می‌فرستد) | هر استریم: `200` + echo فریم‌های DATA + تریلر `grpc-status: 0` (مسیرهای `grpc` و `h2`) |
| `GET /bytes/<n>` یا `?size=<n>` | n بایت داده‌ی تصادفی با `Cache-Control: public, max-age=…` (سناریوی `http`) |
| `GET /__lt/stats` | شمارنده‌های origin به‌صورت JSON |

پورت 8080 را فقط برای IP نود باز کنید (فایروال VM origin).

### ۴.۲ سایت آزمایشی

یک دامنه/سایت آزمایشی روی همان نود بسازید (ترجیحاً در یک پلن داخلی بدون سقف):

1. رکورد proxied سایت → آدرس VM origin با پورت 8080 (برای سناریوی `http`).
2. گواهی TLS فعال (gRPC و h2 فقط روی TLS کار می‌کنند؛ پورت 80 نود فقط HTTP/1.1 است).
3. کش روشن (`cache.enabled`)، و `ignore_query: false` (وگرنه درخواست‌های MISS هم HIT می‌شوند).
4. WAF، چالش DDoS، rate limit و قوانین فایروال برای این سایت **خاموش** (چالش JS پاسخ 503/صفحه‌ی چالش
   برمی‌گرداند و نتیجه را خراب می‌کند).
5. بخش `tunnel` با مسیرهای پیش‌فرض ابزار:

```json
{
  "enabled": true,
  "idle_timeout": 3600,
  "max_connections_per_ip": 0,
  "fallback": "origin",
  "paths": [
    {"id": "ltws",   "path": "/lt-ws",     "protocol": "ws",          "origin": {"address": "ORIGIN_IP", "port": 8080}},
    {"id": "lthu",   "path": "/lt-hu",     "protocol": "httpupgrade", "origin": {"address": "ORIGIN_IP", "port": 8080}},
    {"id": "ltxh",   "path": "/lt-xh",     "protocol": "xhttp",       "origin": {"address": "ORIGIN_IP", "port": 8080}},
    {"id": "ltgrpc", "path": "/lt.Tunnel", "protocol": "grpc",        "origin": {"address": "ORIGIN_IP", "port": 8080}},
    {"id": "lth2",   "path": "/lt-h2",     "protocol": "h2",          "origin": {"address": "ORIGIN_IP", "port": 8080}}
  ]
}
```

6. در پلن سایت آزمایشی `max_tunnel_connections: 0` (نامحدود) و در بخش تونل `max_connections_per_ip: 0`؛
   وگرنه چون همه‌ی اتصال‌ها از یک IP کلاینت می‌آیند، خطای `http_429` می‌گیرید و ظرفیت سقف سایت را
   اندازه می‌گیرید نه ظرفیت نود.

مسیرهای پیش‌فرض ابزار: `http` → `/bytes/16384`، `ws` → `/lt-ws`، `httpupgrade` → `/lt-hu`،
`xhttp` → `/lt-xh`، `grpc` → `/lt.Tunnel/Tun`، `h2` → `/lt-h2` (با `--path` عوض می‌شوند).

## ۵. سناریوها

شکل کلی:

```bash
./pcdn-loadtest <سناریو> --target <IP نود>:443 --host <دامنه‌ی سایت آزمایشی> [گزینه‌ها]
```

- `--target` آدرس **IP** نود (IPv6: `[2001:db8::1]:443`)؛ نام دامنه پذیرفته نمی‌شود تا بار فقط به همان
  یک نودی برسد که نام برده‌اید (نه به هر چیزی که DNS برگرداند).
- `--host` هم Host header و هم SNI است.
- TLS روی پورت 443 خودکار روشن است (`--tls` / `--no-tls` برای حالت‌های دیگر). گواهی به‌صورت پیش‌فرض
  **اعتبارسنجی می‌شود**؛ برای CA آزمایشی `--ca ca.pem` و فقط در صورت نیاز واقعی (گواهی self-signed)
  `--insecure`.

### گزینه‌های مشترک

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `--connections N` | 100 | سشن‌های تونل هم‌زمان (سناریوهای تونل) |
| `--duration S` | 30 | ثانیه‌های حالت پایدار، **پس از** باز شدن همه‌ی اتصال‌ها |
| `--open-rate R` | 200 | اتصال جدید در ثانیه (برای جلوگیری از طوفان SYN) |
| `--mbps M` | 1 | نرخ آپلود هر سشن (echo می‌شود، پس دانلود هم همین‌قدر)؛ `0` = حداکثر ممکن با `--inflight` |
| `--msg-size B` | 16384 | اندازه‌ی هر پیام |
| `--inflight K` | 8 | حداکثر پیام echo‌نشده در هر سشن |
| `--timeout S` | 10 | اگر echo یک پیام بیش از این طول بکشد سشن با `echo_timeout` شکست می‌خورد |
| `--connect-timeout`، `--handshake-timeout` | 10، 15 | مهلت TCP/TLS و کل برقراری سشن |
| `--no-reconnect` | — | سشن قطع‌شده دوباره باز نشود (پیش‌فرض: مثل Xray بعد از ۱ ثانیه دوباره وصل می‌شود) |
| `--header 'K: V'` | — | هدر اضافه |
| `--out FILE` | خودکار | فایل JSON (`-` = خروجی استاندارد) |
| `--quiet` | — | بدون گزارش ثانیه‌به‌ثانیه روی stderr |

### http — ترکیب HIT/MISS کش

```bash
./pcdn-loadtest http --target 203.0.113.10:443 --host lt.example.com \
    --path /bytes/102400 --concurrency 200 --rps 5000 --miss-ratio 0.1 --duration 60
```

`--miss-ratio` سهم درخواست‌هایی است که یک query تصادفی (`?pcdn_lt=…`) می‌گیرند و MISS می‌شوند. هدر
`X-Cache` نود شمرده و نسبت HIT گزارش می‌شود. `--rps 0` یعنی حداکثر سرعت.

### ws / httpupgrade — سشن‌های WebSocket و HTTPUpgrade

```bash
./pcdn-loadtest ws          --target 203.0.113.10:443 --host lt.example.com --connections 2000 --mbps 2 --duration 120
./pcdn-loadtest httpupgrade --target 203.0.113.10:443 --host lt.example.com --connections 2000 --mbps 2 --duration 120
```

### grpc / h2 — استریم‌های HTTP/2

```bash
./pcdn-loadtest grpc --target 203.0.113.10:443 --host lt.example.com --connections 2000 --streams-per-conn 8 --mbps 1
./pcdn-loadtest h2   --target 203.0.113.10:443 --host lt.example.com --connections 500
```

نیاز به TLS و ALPN `h2` دارد (اگر نود h2 را نپذیرد خطای `protocol` می‌گیرید). `--streams-per-conn`
چند سشن را روی یک اتصال HTTP/2 multiplex می‌کند (مثل کلاینت‌های gRPC)؛ سقف استریم هم‌زمان نود 512 است.
`grpc` پیام‌ها را با قالب gRPC (پیشوند ۵ بایتی) می‌فرستد؛ `h2` بایت خام (شبیه XHTTP stream-one).

### xhttp — XHTTP روی HTTP/1.1

```bash
./pcdn-loadtest xhttp --target 203.0.113.10:443 --host lt.example.com --connections 1000 --xhttp-mode packet-up
./pcdn-loadtest xhttp --target 203.0.113.10:443 --host lt.example.com --connections 1000 --xhttp-mode stream-up
```

هر سشن = یک GET طولانی برای دانلود (`<path>/<sid>`) + آپلود: در `packet-up` یک POST به ازای هر بسته
روی یک اتصال keep-alive (`<path>/<sid>/<seq>`)، در `stream-up` یک POST chunked طولانی. پس هر سشن **دو**
اتصال TCP دارد (برای `ulimit` و پورت‌ها حساب کنید). سقف اتصال تونل نود فقط GET را می‌شمارد.

### ramp — افزایش پله‌ای تا نقطه‌ی شکست

```bash
./pcdn-loadtest ramp --protocol ws --target 203.0.113.10:443 --host lt.example.com \
    --start 200 --step 200 --step-duration 30 --max 10000 --mbps 2 \
    --max-error-rate 0.01 --max-p99-ms 500
```

در هر پله `--step` سشن اضافه می‌شود (سشن‌های قبلی باز می‌مانند) و پس از `--step-duration` ثانیه
سنجیده می‌شود. پله **رد** می‌شود اگر:

- نرخ خطا (باز نشدن + قطع سشن + echo_timeout، تقسیم بر تلاش‌ها) از `--max-error-rate` بیشتر شود؛
- p99 تأخیر رفت‌وبرگشت (برای `--protocol http`: زمان کامل درخواست) از `--max-p99-ms` بیشتر شود؛
- همه‌ی سشن‌های هدف برقرار نمانند (`sessions_not_held`)؛
- یا حلقه‌ی رویداد خود کلاینت بیش از `--max-client-lag-ms` (250) عقب بیفتد (`client_saturated`):
  یعنی کلاینت گلوگاه است؛ نتیجه کران پایین است، کلاینت بیشتر اضافه کنید.

«بیشینه‌ی اتصال پایدار» = هدف آخرین پله‌ی قبول‌شده. `--protocol` می‌تواند `http` هم باشد (پله‌ها
تعداد اتصال keep-alive را بالا می‌برند).

### merge — جمع‌کردن چند کلاینت

```bash
# روی هر VM / هر پروسه با out جدا، هم‌زمان:
./pcdn-loadtest ws ... --connections 3000 --out c1.json
./pcdn-loadtest ws ... --connections 3000 --out c2.json
# سپس:
./pcdn-loadtest merge c1.json c2.json --out total.json
```

اتصال‌ها، Mbps و خطاها جمع می‌شوند و p50/p95/p99 از هیستوگرام خام (`raw`) همه‌ی اجراها دقیق محاسبه
می‌شود. اجراها باید هم‌زمان شروع شوند و مدت یکسان داشته باشند.

### آستانهٔ قبول/رد (دروازهٔ staging)

سناریوهای ثابت (`http`، `ws`، `httpupgrade`، `grpc`، `h2`، `xhttp`) دو گزینهٔ اختیاری دارند که اجرا را به یک
آزمون قبول/رد تبدیل می‌کنند (SPEC §23.1):

| گزینه | معنا |
|---|---|
| `--max-error-pct PCT` | اگر نرخ خطا (همان `error_rate` گزارش، به درصد) از `PCT` بیشتر شود، رد |
| `--max-p99-ms MS` | اگر p99 تأخیر (http: زمان کامل درخواست؛ تونل‌ها: رفت‌وبرگشت echo) از `MS` بیشتر شود یا اصلاً اندازه‌گیری نشود، رد |

بدون این گزینه‌ها رفتار مثل قبل است (کد خروج ۰). با آن‌ها گزارش JSON بخش `thresholds`
(`{"max_error_pct", "max_p99_ms", "error_pct", "p99_ms", "pass", "failures"}`) می‌گیرد و در صورت رد، کد خروج
**۳** است. دروازهٔ انتشار (`tools/release/staging-verify.sh`، [RELEASE §۴](RELEASE.md#۴-دروازهٔ-staging-staging-verifysh))
این‌ها را با پیش‌فرض‌های زیر روی یک نود staging اجرا می‌کند:

```bash
./pcdn-loadtest http --target 203.0.113.10:443 --host lt.staging.example.com --duration 120 \
    --max-error-pct 0.5 --max-p99-ms 1500 --out http.json
./pcdn-loadtest ws --target 203.0.113.10:443 --host lt.staging.example.com --duration 60 \
    --max-error-pct 0.5 --out ws.json
```

(`ramp` آستانه‌های پله‌ای خودش را دارد: `--max-error-rate` به‌صورت کسر و `--max-p99-ms`.)

## ۶. خواندن نتایج

خلاصه‌ی فارسی در پایان هر اجرا چاپ می‌شود؛ نمونه:

```
══════ خلاصه‌ی آزمون بار pcdn-loadtest ══════
سناریو: ws | هدف: 203.0.113.10:443 | Host/SNI: lt.example.com | TLS: بله | مدت: 135 ثانیه
بیشینه‌ی اتصال پایدار: 2000 (هدف 2000, اوج هم‌زمان 2000, باز شده 2000, ناموفق در باز شدن 0, قطع‌شده 0)
پهنای باند (Mbps): میانگین کل 7980.4 | بالا (کلاینت→نود) 3990.1 | پایین (نود→کلاینت) 3990.3 | اوج ۱ثانیه‌ای 8102.7
برآورد ترافیک خروجی نود (tx): حدود 7980.4 Mbps
تأخیر رفت‌وبرگشت echo (ms): p50=4.1 | p95=9.8 | p99=21.5
زمان برقراری اتصال/دست‌دهی (ms): p50=6.2 | p95=11.0 | p99=35.9
نرخ خطا: 0.000٪
خطا: هیچ
```

فیلدهای اصلی JSON (`result`):

| فیلد | معنی |
|---|---|
| `max_sustainable_connections` | سناریوی ثابت: کمترین تعداد سشن فعال در حالت پایدار؛ ramp: هدف آخرین پله‌ی قبول |
| `connections` | `target`، `opened`، `open_failed`، `dropped`، `peak_active`، `attempts` |
| `throughput_mbps` | `up`، `down`، `total` (میانگین حالت پایدار) و `peak_1s_total` |
| `node_tx_estimate_mbps` | برآورد tx کارت شبکه‌ی نود (تونل: up+down؛ http: down) |
| `latency_ms.rtt` | تأخیر رفت‌وبرگشت echo هر پیام (کلاینت→نود→origin→نود→کلاینت): `p50/p95/p99/max/n` |
| `latency_ms.connect` | TCP + TLS + Upgrade/پاسخ HTTP/2 تا آماده‌شدن سشن |
| `latency_ms.request`، `ttfb` | سناریوی http: زمان کامل و زمان اولین بایت |
| `requests` | http: `total`، `rps`، `status`، `cache` (مقادیر X-Cache)، `hit_ratio` |
| `errors` | شمارش خطا به تفکیک نوع؛ `error_rate` نسبت آن به تلاش‌ها |
| `capacity_hint_mbps` | فقط ramp: کل Mbps در آخرین پله‌ی قبول (نقطه‌ی شروع برای بخش ۷) |
| `steps` | فقط ramp: نتیجه‌ی هر پله |
| `timeline` | نمونه‌ی ثانیه‌به‌ثانیه: سشن فعال، Mbps، خطا، تأخیر حلقه‌ی کلاینت |
| `client.warnings` | هشدارهای گلوگاه کلاینت (حلقه‌ی رویداد، فایل‌باز، پورت محلی) |

### انواع خطا

| نوع | معنی | دسته در تله‌متری نود (SPEC §15.1) |
|---|---|---|
| `http_429`، `http_503` | سقف اتصال سایت/IP یا fair share | `limit` |
| `http_403` | کشور مجاز نیست / فایروال / IP مسدود | `country` |
| `http_426`، `http_400`، `protocol` | پروتکل اشتباه برای مسیر، نبود ALPN h2، 101 نیامد | `protocol` |
| `http_502` | نود به origin وصل نشد | `origin_refused` |
| `http_504` | مهلت اتصال/پاسخ origin | `origin_timeout` |
| `h2_refused_stream`، `goaway` | سقف استریم HTTP/2 یا بسته‌شدن اتصال | — |
| `echo_timeout` | داده رفت ولی در `--timeout` برنگشت: صف‌شدن/اشباع در مسیر | (معمولاً `abnormal`) |
| `closed`، `reset` | اتصال برقرار وسط کار بسته/reset شد | `abnormal` |
| `connect_refused`، `connect_timeout`، `tls_*` | لایه‌ی TCP/TLS (backlog پر، فایروال، گواهی) | — |
| `client_fd_limit`، `client_ports` | محدودیت **کلاینت** | — |

هم‌زمان با آزمون، صفحه‌ی «کیفیت تونل» سایت آزمایشی (SPEC §15.3) همین خطاها را از دید نود نشان می‌دهد؛
اختلاف زیاد بین دو دید معمولاً یعنی گلوگاه بین کلاینت و نود (شبکه) است.

**تفسیر.** تا زمانی که `error_rate` صفر و p99 پایدار است، نود هنوز جا دارد. اولین علامت اشباع
معمولاً رشد p99 و سپس `echo_timeout` است؛ رشد `connect` (به‌خصوص p99 دست‌دهی TLS) یعنی CPU نود یا
backlog. همیشه `client.warnings` را نگاه کنید: اگر کلاینت اشباع شده، عدد به‌دست‌آمده سقف نود نیست.

## ۷. به‌دست‌آوردن capacity_mbps

`capacity_mbps` نود (پنل → Edges، یا `PATCH /api/v1/edges/{id}` با `{"capacity_mbps": N}`، یا
`CAPACITY_MBPS` در `agent.conf`) سه کار انجام می‌دهد: shedding از DNS در ۹۰٪
(`EDGE_SHED_PERCENT`)، داغ‌شدن fair share در ۸۵٪، و هشدار ظرفیت گروه در ۷۰٪ (SPEC §7.4، §15.2، §15.5).
همه با `tx_mbps` نود (ترافیک خروجی کارت شبکه) مقایسه می‌شوند. پس `capacity_mbps` باید **بیشترین tx که
نود بدون افت کیفیت تحمل می‌کند** باشد. روش:

1. **نود را از DNS خارج کنید** (در پنل غیرفعال، یا نود تازه که هنوز فعال نشده) تا کاربران واقعی در
   آزمون نباشند. `CAPACITY_MBPS` را موقتاً 0 بگذارید تا shedding/fair share وسط آزمون فعال نشوند.
2. **ramp با بار واقعی‌نما.** نرخ هر سشن را از آمار واقعی بگیرید (میانگین Mbps هر سشن در «مصرف تونل»؛
   معمولاً ۰٫۵ تا ۳). برای ترکیب پروتکل‌ها چند کلاینت هم‌زمان با پروتکل‌های مختلف اجرا کنید (مثلاً
   ۶۰٪ ws، ۳۰٪ grpc، ۱۰٪ xhttp به نسبت کاربران واقعی).
   ```bash
   ./pcdn-loadtest ramp --protocol ws --target NODE_IP:443 --host lt.example.com \
       --mbps 2 --start 250 --step 250 --step-duration 60 --max 20000 --max-p99-ms 300
   ```
3. **هم‌زمان روی نود ببینید:** `sar -n DEV 1` (tx واقعی کارت شبکه)، `top`/`mpstat -P ALL 1` (CPU کارگرهای
   nginx و softirq)، `ss -s`، و `tx_mbps` در heartbeat پنل. اگر tx واقعی با `node_tx_estimate_mbps`
   نمی‌خواند (مثلاً origin روی همان نود است) عدد کارت شبکه را مبنا بگیرید.
4. **نقطه‌ی زانو:** آخرین پله‌ای که قبول شد (`capacity_hint_mbps`) = `T_ok`. یک اجرای ثابت با همان تعداد
   سشن و `--duration 600` بزنید تا پایداری ۱۰ دقیقه‌ای تأیید شود.
5. **عدد نهایی:**
   ```
   capacity_mbps = floor( min( T_ok , 0.95 × سرعت پورت , پهنای باند قراردادی دیتاسنتر ) )
   ```
   چون shedding در ۹۰٪ و fair share در ۸۵٪ همین عدد فعال می‌شوند، نود **قبل** از رسیدن به نقطه‌ی افت
   کیفیت از DNS خارج یا محافظت می‌شود. حاشیه‌ی اضافه لازم نیست مگر آزمون از کلاینت‌هایی با مسیر شبکه‌ی
   متفاوت از کاربران واقعی انجام شده باشد (آن‌وقت ۱۰٪ کم کنید).
6. **مثال:** پورت 10G، قرارداد 8 Gbps، ramp با 2 Mbps/سشن تا 3600 سشن (≈ 7.2 Gbps tx) سالم بوده و در
   4000 سشن p99 از 300ms گذشته ← `capacity_mbps = min(7200, 9500, 8000) = 7200`. shedding در 6480 و
   fair share در 6120 Mbps فعال می‌شوند.
7. نودهای هم‌سخت‌افزار را می‌توانید با یک اجرای ثابت در `0.9 × capacity` تأیید کنید و همان عدد را بدهید.
   پس از تنظیم، `CAPACITY_MBPS` در `agent.conf` را برگردانید (یا خالی بگذارید تا عدد پنل اعمال شود).

برای سناریوی `http` (نودهای عمومی) همین روش با `ramp --protocol http` و `--miss-ratio` واقعی (نسبت MISS
سایت‌ها) انجام می‌شود؛ آن‌جا `node_tx_estimate_mbps` برابر `down` است.

## ۸. fair share و سقف‌های تونل

- **fair share** (SPEC §15.2/§15.8) فقط وقتی نود «داغ» است (≥ ۸۵٪ `capacity_mbps`) سشن‌های **جدید** سایتی
  را که بیش از `fair_share_pct` (پیش‌فرض ۲۵) از بازکردن‌های اخیر را دارد با 429 رد می‌کند؛ سشن‌های برقرار
  دست نمی‌خورند. پس بدون `capacity_mbps` درست (بخش ۷) fair share هرگز کار نمی‌کند.
- انتخاب `fair_share_pct`: اگر نود معمولاً k سایت تونل فعال پرمصرف دارد، مقداری کمی بالاتر از `100/k`
  مناسب است (۴ سایت یا بیشتر → ۲۵؛ ۲ سایت → ۵۰ تا ۶۰). مقدار خیلی کم باعث 429 برای سایت‌های عادی در ساعات
  اوج می‌شود.
- **max_tunnel_connections پلن‌ها:** از آزمون بخش ۷ تعداد سشن پایدار نود `N_max` را دارید
  (`≈ capacity_mbps ÷ Mbps هر سشن`). سقف هر سایت روی هر نود را طوری بگذارید که یک سایت به‌تنهایی نود را پر
  نکند: `max_tunnel_connections ≈ N_max × fair_share_pct / 100` (مثال بالا: 3600 × 0.25 = 900).
- `per_connection_mbps` روی nginx 1.24 **اعمال نمی‌شود** (EDGE.md)؛ اهرم‌های واقعی سقف اتصال سایت
  (`max_tunnel_connections`)، سقف اتصال هر IP (`max_connections_per_ip`) و fair share هستند.
- برای دیدن رفتار fair share در عمل (اختیاری): `capacity_mbps` را موقتاً روی عددی کمتر از باری که تولید
  می‌کنید بگذارید و با دو سایت آزمایشی هم‌زمان ramp کنید؛ سایت غالب باید `http_429` بگیرد و سایت دیگر نه.

## ۹. نکات ایمنی

- فقط روی نودهای خودتان، با IP صریح. ابزار نام دامنه را نمی‌پذیرد، redirect دنبال نمی‌کند و جز همان
  `IP:port` به جایی وصل نمی‌شود.
- قبل از آزمون‌های سنگین به دیتاسنترِ هر دو طرف (کلاینت و نود) اطلاع دهید؛ سامانه‌ی ضد DDoS آن‌ها ممکن
  است IP کلاینت یا نود را مسدود (blackhole) کند.
- نود عملیاتی را حین آزمون از DNS خارج کنید یا آزمون را خارج از ساعات اوج انجام دهید؛ آزمون سنگین روی
  نود پر کاربران واقعی را کند می‌کند.
- ترافیک آزمون واقعاً مصرف می‌شود: هزینه‌ی پهنای باند دیتاسنتر، و در صورتحساب سایت آزمایشی (ترافیک
  تونل هر دو جهت حساب می‌شود). از پلن داخلی بدون سقف/بدون صورتحساب استفاده کنید.
- برای سایت آزمایشی از دامنه‌ی جداگانه استفاده کنید، نه سایت مشتری.
- `--insecure` را فقط برای گواهی آزمایشی self-signed به‌کار ببرید؛ پیش‌فرض اعتبارسنجی گواهی است.
- origin آزمایشی هر داده‌ای را echo می‌کند: پورت آن را فقط برای IP نودها باز کنید و پس از آزمون خاموشش کنید.
- قطع اضطراری: `Ctrl+C` (همه‌ی اتصال‌ها بسته می‌شوند)؛ مدت هر اجرا محدود به `--duration` یا پله‌های ramp است.

## ۱۰. محدودیت‌های ابزار

- **یک هسته در هر پروسه.** Python/asyncio روی یک هسته بسته به TLS و اندازه‌ی پیام از حدود ۱ Gbps (TLS، پیام کوچک) تا چند Gbps (بدون TLS، پیام بزرگ) یا
  چند هزار پیام در ثانیه تولید می‌کند. برای بیشتر: چند پروسه/VM و `merge`، پیام بزرگ‌تر (`--msg-size 65536`)،
  و `uvloop`. هشدار `client event loop lagged` یعنی به این سقف رسیده‌اید.
- **HTTP/2 حداقلی:** فریم‌بندی و کنترل جریان کامل است، اما HPACK فقط رمزگذاری literal (همیشه معتبر)
  و از پاسخ فقط `:status` را می‌خواند. برای آزمون بار کافی است ولی کلاینت عمومی HTTP/2 نیست.
- **XHTTP** روی HTTP/1.1 پیاده شده (packet-up و stream-up)؛ XHTTP روی HTTP/2 را با سناریوی `h2`
  (stream-one) بسنجید. در packet-up پست‌ها ترتیبی‌اند (یکی در لحظه برای هر سشن).
- WebSocket روی HTTP/2 (RFC 8441) و HTTP/3 پشتیبانی نمی‌شوند (نود هم ws را فقط روی HTTP/1.1 پروکسی می‌کند).
- **ramp** در یک پروسه اجرا می‌شود؛ برای ramp بزرگ‌تر از توان یک پروسه، چند پروسه‌ی سناریوی ثابت با
  تعداد سشن‌های پله‌ای اجرا و `merge` کنید.
- تأخیر گزارش‌شده رفت‌وبرگشت کامل تا origin است (شامل مسیر نود→origin)؛ origin را نزدیک نود بگذارید.
- `node_tx_estimate_mbps` فرض می‌کند origin روی ماشینی جدا از نود است و ترافیک دیگری روی نود نیست.

## ۱۱. تست‌های خودکار کیت

```bash
python3 -m pytest -q tools/loadtest/tests          # حدود ۵۰ ثانیه
PCDN_LOADTEST_NO_EDGE=1 python3 -m pytest -q tools/loadtest/tests   # فقط تست‌های بدون nginx (~۳۰ ثانیه)
```

- `test_loadtest.py`: همه‌ی سناریوها مستقیم روی `origin.py` (TLS/ALPN، اعتبارسنجی گواهی، طبقه‌بندی خطا،
  ramp، merge، کنترل جریان HTTP/2 با پنجره‌ی ۶۴KB، دقت صدک‌ها) و امتناع از اجرا بدون `--target`.
- `test_edge_e2e.py`: همان سناریوها از طریق یک نود واقعی (nginx + njs + پیکربندی رندرشده‌ی agent، با
  همان harness `edge/tests`)، به‌علاوه‌ی HIT کش، 429 سقف اتصال هر IP و 426 پروتکل اشتباه. اگر nginx و
  ماژول‌های نود (یا `mmdb_writer`) نصب نباشند خودکار skip می‌شود و مانند `edge/tests` باید با root اجرا شود.
