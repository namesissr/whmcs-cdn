## پیش‌نیازها

- یک سرور تازه **Ubuntu 24.04 LTS** با دسترسی root (یا sudo) و IP عمومی.
- دامنه عمومی سرور مرکزی (کنترلر) که با متغیر `CONTROLLER_DOMAIN` در `.env` تنظیم شده است
  (مثلاً `cdn-api.pasargadmizban.com`). نودها بسته و پیکربندی را از همین آدرس می‌گیرند.
- یک «توکن یک‌بارمصرف» برای هر نود که هنگام ساخت نود در پنل WHMCS (یا API مدیریتی) صادر می‌شود و
  فقط همان یک‌بار نمایش داده می‌شود.
- پورت‌های 80 و 443 باز باشند؛ اگر IPv6 دارید، هر دو خانواده آدرس به کنترلر برسند.

> بسته‌ی نود (`/edge/bundle.tar.gz`) فقط شامل عامل (agent) و قالب‌های متن‌باز است و **هیچ رمز،
> کلید یا توکنی ندارد**؛ بنابراین مسیرهای `GET /edge/bootstrap.sh`، `GET /edge/bundle.tar.gz` و
> `GET /edge/version` روی کنترلر بدون احراز هویت سرو می‌شوند.

## ۱. نصب تک‌دستوری

پس از ساخت نود در پنل و گرفتن توکن، روی سرور نود این تک‌دستور را اجرا کنید:

```bash
curl -fsSL https://<controller>/edge/bootstrap.sh | sudo PCDN_EDGE_TOKEN=edge_xxxxxxxx bash -s -- \
    --controller https://<controller>
```

توکن از متغیر محیطی `PCDN_EDGE_TOKEN` خوانده می‌شود تا در فهرست پروسه‌ها (`ps`) دیده نشود؛ `--token`
هنوز پشتیبانی می‌شود. اتصال به کنترلر فقط با https مجاز است مگر `--insecure-http` بدهید.

`bootstrap.sh` بسته را از کنترلر دانلود می‌کند، باز می‌کند و `install.sh` را با همان پرچم‌ها اجرا
می‌کند. پرچم‌های قابل انتقال:

| پرچم | توضیح |
|---|---|
| `--region home\|global` | منطقه/استخر DNS نود (پیش‌فرض `global`) |
| `--role general\|tunnel` | نقش نود که به «گروه» نود نگاشت می‌شود (پیش‌فرض `general`) |
| `--cache-size 50g` | حداکثر فضای کش هر سایت (پیش‌فرض `10g`) |
| `--http-port N` / `--https-port N` | پورت‌های عمومی (پیش‌فرض 80/443) |
| `--no-ipv6` | گوش‌ندادن روی IPv6 |
| `--no-geoip` | دانلود نشدن پایگاه کشور DB-IP |
| `--upgrade` | به‌روزرسانی نود نصب‌شده در جا (بخش ۶) |

رشته‌ی آماده‌ی هر نود (شامل توکن) در پنل WHMCS، صفحه‌ی «نودها» نمایش داده می‌شود؛ یا از API:

```bash
curl -s -H "Authorization: Bearer $ADMIN_API_KEY" \
  "https://<controller>/api/v1/edges/install?token=edge_xxx&region=home&role=tunnel"
# => {"command": "curl -fsSL https://<controller>/edge/bootstrap.sh | sudo bash -s -- ..."}
```

بررسی سلامت پس از نصب:

```bash
systemctl status pcdn-agent
journalctl -u pcdn-agent -f
curl -H 'Host: health.pcdn' http://127.0.0.1/__pcdn/health
```

> اگر کنترلر بسته را سرو نکند (متغیر `EDGE_BUNDLE_DIR` تنظیم/موجود نباشد)، هر دو مسیر بسته 404 با
> پیام روشن برمی‌گردانند و پنل به روش دستی (git/scp) ارجاع می‌دهد. مسیر نصب دستی در EDGE.md آمده است.

## ۲. افزودن گروهی نودها

برای بالا آوردن چند نود هم‌زمان، از API مدیریتی استفاده کنید:

```bash
curl -s -X POST -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"count": 5, "region": "home", "group": "tunnel", "name_prefix": "ir", "capacity_mbps": 1000}' \
  "https://<controller>/api/v1/edges/batch"
```

پاسخ، آرایه‌ای از نودهای ساخته‌شده است؛ هر عضو شامل مشخصات نود، `token` یک‌بارمصرف و `install`
(همان تک‌دستور آماده) است. نام‌ها به‌صورت `name_prefix-<شماره>` و بدون تداخل با نام‌های موجود ساخته
می‌شوند (`count` بین 1 تا 50). در پنل WHMCS همین کار با فرم «افزودن گروهی» انجام می‌شود و فهرست
دستورهای آماده برای کپی نمایش داده می‌شود.

IP نود در زمان ساخت گروهی نامشخص است؛ نود در نخستین heartbeat خود را معرفی می‌کند و تا آنلاین‌شدن
وارد پاسخ‌های DNS نمی‌شود.

## ۳. منطقه و نقش (region / role)

- **region**: `home` (نودهای داخل کشور) یا `global`. تعیین می‌کند نود در کدام استخر GeoDNS پاسخ دهد.
- **role**: `general` یا `tunnel`؛ به «گروه» نود نگاشت می‌شود و مشخص می‌کند نود به سایت‌های پلن عادی
  خدمت دهد یا به سایت‌های حالت تونل (VPN-over-CDN، SPEC §7.4).

منطقه و نقش هنگام **ساخت نود** روی کنترلر تعیین می‌شوند (پنل یا `POST /api/v1/edges[/batch]`) و در
تک‌دستور نصب همان نود گنجانده می‌شوند. `install.sh` این مقادیر را در `/etc/pcdn/agent.conf`
(`REGION=` و `GROUP=`) ذخیره می‌کند و عامل آن‌ها را **فقط در نخستین heartbeat** گزارش می‌دهد تا یک
نود تازه خودکار در استخر درست ثبت شود. تغییرهای بعدی اپراتور از طریق پنل، دیگر با heartbeatها بازنویسی
نمی‌شوند. برای جابه‌جایی یک نود موجود بین استخرها از پنل (یا `PATCH /api/v1/edges/{id}`) استفاده کنید.

## ۴. نصب خودکار با cloud-init

برای بالا آمدن خودکار در نخستین بوت، محتوای `edge/cloud-init.yaml.example` را در بخش «user data»
ماشین قرار دهید و دو مقدار `CONTROLLER` و `TOKEN` (و در صورت نیاز region/role) را جایگزین کنید. این
قالب همان تک‌دستور نصب را اجرا می‌کند.

## ۵. خواندن لاگ‌های نود

هر نود فقط خطوط مشکل‌دار عملیاتی (`warn`/`error`/`crit`) از لاگ خطای nginx و لاگ خود عامل را، روی
کادنس heartbeat، به `POST /edge/v1/logs` می‌فرستد. لاگ دسترسی (access)، بدنه‌ی درخواست‌ها، IP بازدید‌کننده‌ها،
توکن‌ها و کلیدها **هرگز** ارسال نمی‌شوند (IPها و توکن‌ها روی نود سانیتایز می‌شوند). حجم هم محدود است:
حداکثر ~۴۰ خط در هر گزارش و ~۵۰۰ کاراکتر در هر خط، و روی کنترلر یک حلقه‌ی سقف‌دار (~۱۲۰ خط / ~۱۶ کیلوبایت،
قدیمی‌ترها حذف می‌شوند) نگه‌داری می‌شود؛ پس یک نود پرسروصدا نمی‌تواند کنترلر را پر کند.

مشاهده‌ی لاگ‌های یک نود:

```bash
curl -s -H "Authorization: Bearer $ADMIN_API_KEY" \
  "https://<controller>/api/v1/edges/<id>/logs"
# => {"name": "...", "logs_at": "...Z", "lines": [{"t","level","msg"}, ...]}
```

خطوط به‌صورت «قدیمی→جدید» (newest last) ذخیره می‌شوند؛ رابط کاربری آن‌ها را برعکس (جدیدترین بالا) و
با رنگ‌بندی سطح نمایش می‌دهد. در پنل WHMCS، صفحه‌ی «نودها» دکمه‌ی «لاگ‌ها» برای هر نود دارد. فهرست
`GET /api/v1/edges` هم دو نشانگر سبک `logs_at` و `has_logs` دارد (بدون خود خطوط).

## ۶. به‌روزرسانی یک نود

به‌روزرسانی یعنی اجرای دوباره‌ی همان تک‌دستور با پرچم `--upgrade`؛ هیچ کد از راه دور push نمی‌شود.
کنترلر، بسته را به‌روز سرو می‌کند و `--upgrade` تنظیمات موجود (controller، token، پورت‌ها، IPv6، اندازه
کش، region و role) را از `/etc/pcdn/agent.conf` می‌خواند:

```bash
curl -fsSL https://<controller>/edge/bootstrap.sh | sudo bash -s -- \
    --controller https://<controller> --upgrade
```

نسخه‌ی بسته‌ی درحال‌اجرا را عامل در heartbeat گزارش می‌دهد (`bundle_version`) و کنترلر آن را با نسخه‌ی
جاری بسته مقایسه می‌کند:

```bash
curl -s https://<controller>/edge/version       # => {"version": "<hash>"}
```

اگر نسخه‌ی نود عقب باشد، پنل نشان «به‌روزرسانی موجود است» را برای آن نود نمایش می‌دهد.

## ۷. از رده خارج کردن نود (Decommission)

1. ابتدا نود را در پنل **غیرفعال** کنید (یا `PATCH /api/v1/edges/{id}` با `{"enabled": false}`)؛
   این کار آن را از پاسخ‌های DNS خارج می‌کند تا ترافیک تازه نگیرد.
2. چند دقیقه صبر کنید تا اتصال‌های باز تخلیه شوند و TTL رکوردها منقضی شود.
3. روی نود سرویس‌ها را متوقف کنید: `systemctl disable --now pcdn-agent nginx`.
4. در پایان نود را **حذف** کنید (`DELETE /api/v1/edges/{id}` یا دکمه‌ی حذف در پنل)؛ توکن نیز باطل
   می‌شود. سرور را می‌توانید نابود کنید.

## ۸. جدول عیب‌یابی

| نشانه | علت محتمل | بررسی / راه‌حل |
|---|---|---|
| نود آفلاین (بدون heartbeat) | عامل متوقف است یا کنترلر/شبکه در دسترس نیست | `systemctl status pcdn-agent`؛ `journalctl -u pcdn-agent -f`؛ دسترسی به `https://<controller>/edge/version`؛ درستی `CONTROLLER_URL` و `EDGE_TOKEN` در `/etc/pcdn/agent.conf` |
| probe خطا می‌دهد ولی heartbeat سالم است («گزارش می‌دهد اما خراب») | nginx بالا نیست یا `/__pcdn/health` پاسخ نمی‌دهد | `nginx -t`؛ `systemctl status nginx`؛ `curl -H 'Host: health.pcdn' http://127.0.0.1/__pcdn/health`؛ باز بودن پورت 80 از سمت کنترلر |
| پروب تونل خراب است ولی تونل‌ها واقعاً کار می‌کنند / تغییرات کانفیگ روی نود اعمال نمی‌شود | `/run/nginx.pid` خالی یا کهنه است، پس `nginx -s reload` (و `systemctl reload nginx`) با `invalid PID number ""` شکست می‌خورد و nginx همان کانفیگ قدیمی را سِرو می‌کند | `cat /run/nginx.pid`؛ `journalctl -u pcdn-agent | grep -i "nginx reload failed"`؛ عامل از نسخهٔ جدید خودش فایل pid را از مستر در حال اجرا بازنویسی و reload را تکرار می‌کند (و در نهایت SIGHUP می‌فرستد) و همین را در لاگ هشدار می‌دهد؛ اگر nginx اصلاً بالا نیست: `pcdn-agent drain` ← `systemctl restart nginx` ← `pcdn-agent undrain` |
| خطای پیکربندی (config error) پس از سینک | قالب یا گواهی نامعتبر، `nginx -t` شکست خورده | لاگ‌های نود (`/api/v1/edges/{id}/logs`) و `journalctl -u pcdn-agent`؛ عامل پیکربندی بد را rollback می‌کند و خطا را در heartbeat گزارش می‌دهد |
| نود اشباع/شِد (`shed`) | مصرف پهنای‌باند از `capacity_mbps` عبور کرده | ظرفیت نود را در پنل تنظیم کنید یا نود بیشتری اضافه کنید؛ نود پس از افت بار خودکار برمی‌گردد (SPEC §7.4) |
| مشکل گواهی (cert) | صدور/تمدید ACME ناموفق یا گواهی منقضی | بخش گواهی‌ها در OPERATIONS.md؛ هشدار `alert_cert_days`؛ لاگ‌های نود برای خطای SSL |
| «به‌روزرسانی موجود است» | نسخه‌ی بسته‌ی نود عقب است | اجرای تک‌دستور با `--upgrade` (بخش ۶) |
| نصب: دانلود بسته ناموفق | کنترلر در دسترس نیست یا `EDGE_BUNDLE_DIR` تنظیم نیست | دسترسی به `https://<controller>/edge/bundle.tar.gz`؛ تنظیم `EDGE_BUNDLE_DIR` روی کنترلر یا نصب دستی (EDGE.md) |

| آدرس اضافی نود قطع است (`edge_address_down`) | یک آدرس اضافی نود از سمت کنترلر پاسخ نمی‌دهد | همان بررسی‌های ردیف probe، اما برای آن آدرس؛ آدرس پس از `PROBE_FAIL_CHECKS` شکست پیاپی خودکار از DNS خارج می‌شود و با اولین probe موفق برمی‌گردد (بخش ۹) |

برای پایش کلی نودها، صفحه‌ی وضعیت عمومی و رخدادها، بخش ۸ [OPERATIONS.md](OPERATIONS.md#۸-پایش-سلامت-نودها-صفحه-وضعیت-عمومی-و-رخدادها-spec-8) را ببینید.

## ۹. آدرس‌های چندگانه‌ی نود و failover مبتنی بر سلامت (SPEC §12)

هر نود یک آدرس **اصلی** دارد (`ipv4`/`ipv6` که هویت نود است و با ویرایش نود تغییر می‌کند و
حذف نمی‌شود) و می‌تواند **آدرس‌های اضافی** هم داشته باشد. کنترلر آزمون سلامت (probe §8.1) را
روی «هر» آدرس فعال اجرا می‌کند و ترافیک را فقط روی آدرس‌های سالم نگه می‌دارد؛ این یک قابلیت
افزونگی/آپ‌تایم برای آدرس‌هایی است که واقعاً از سمت کنترلر در دسترس نیستند و **هیچ** کنترل
«جابه‌جایی دستی آدرس» یا تشخیص فیلترینگ ندارد.

مدیریت آدرس‌ها (پنل WHMCS، پنل «آدرس‌ها»، یا API مدیریت):

```bash
# فهرست آدرس‌ها (اصلی + اضافی) همراه با سلامت هرکدام
curl -s -H "Authorization: Bearer $ADMIN_API_KEY" https://<controller>/api/v1/edges/<id>/addresses
# افزودن یک آدرس اضافی
curl -s -X POST -H "Authorization: Bearer $ADMIN_API_KEY" \
  -d '{"family":4,"ip":"5.160.1.20","label":"link-2"}' https://<controller>/api/v1/edges/<id>/addresses
# ویرایش/فعال یا غیرفعال کردن (نگه‌داری) / حذف یک آدرس اضافی
curl -s -X PATCH  -H "Authorization: Bearer $ADMIN_API_KEY" -d '{"enabled":false}' https://<controller>/api/v1/edges/<id>/addresses/<aid>
curl -s -X DELETE -H "Authorization: Bearer $ADMIN_API_KEY" https://<controller>/api/v1/edges/<id>/addresses/<aid>
```

قواعد نمایش در DNS:

- یک آدرس وقتی **آگهی (advertised)** می‌شود که «فعال» باشد و probe آن سالم باشد یا هنوز probe
  نشده باشد؛ پس از `PROBE_FAIL_CHECKS` شکست پیاپی از DNS **خارج** می‌شود و با اولین probe موفق
  برمی‌گردد. `enabled=false` (نگه‌داری) بلافاصله آن را خارج می‌کند.
- **همیشه fail-open:** اگر خارج‌کردنِ آدرس‌های ناسالم باعث شود مجموعه‌ی یک خانواده برای یک
  منطقه/گروه **خالی** شود، آن خارج‌سازی نادیده گرفته می‌شود و آدرس‌های شناخته‌شده باز هم آگهی
  می‌شوند؛ زون هرگز به‌خاطر وضعیت سلامت خالی نمی‌شود.
- اصلاح آدرس اصلی از همان مسیر ویرایش نود (`PATCH /api/v1/edges/{id}`) انجام می‌شود؛ آدرس اصلی
  حذف‌شدنی نیست.

## ۱۰. رفتار DNS و سلامت نودها (تنظیمات کنترلر)

این بخش رفتارهای خودکارِ DNS و پایش سلامت را که برای پایداری بیشتر (به‌ویژه برای تونل) بهبود
یافته‌اند توضیح می‌دهد. همه‌ی تنظیمات زیر **متغیرهای محیطی کنترلر** هستند (در `.env` / `.env.example`
سرور مرکزی تعریف می‌شوند، نه روی نودها)؛ مقادیر پیش‌فرض برای اکثر استقرارها مناسب‌اند و معمولاً
نیازی به تغییرشان نیست.

- **محافظ قطع ارتباط صفحه‌ی کنترل — `EDGE_SILENT_GUARD_FRACTION` (پیش‌فرض `0.5`).** اگر در یک چرخه‌ی
  زمان‌بند مجموعه‌ی نودهای آنلاین (آن‌هایی که heartbeat می‌دهند) بیش از این کسر کوچک شود، کنترلر آن
  را «قطعِ مسیر کنترل» تلقی می‌کند، نه مرگِ هم‌زمانِ ده‌ها نود: DNS قبلی را نگه می‌دارد و هشدار بحرانی
  می‌دهد، به‌جای خالی/کوچک‌کردن pool. فقط وقتی `EDGE_PROBE` روشن است فعال می‌شود (آنگاه ifurlup
  پاوردی‌ان‌اس همچنان نودهای واقعاً مرده را در ~۵ ثانیه حذف می‌کند). مقدار `0` این محافظ را غیرفعال
  می‌کند. سایت‌های تونل هیچ‌گاه به origin خام fallback نمی‌شوند.

- **هیسترزیس load shedding (F25).** یک نمونه‌ی ۶۰ ثانیه‌ای دیگر بلافاصله نود را shed نمی‌کند:
  `EDGE_SHED_CHECKS` (پیش‌فرض `3`) گزارشِ پیاپی در/بالای `EDGE_SHED_PERCENT` (پیش‌فرض `90`٪ از
  `capacity_mbps`) لازم است، نود دست‌کم `EDGE_SHED_HOLD` ثانیه (پیش‌فرض `300`) shed می‌ماند و تنها
  زیرِ `EDGE_SHED_PERCENT − 15`٪ برمی‌گردد. در هر چرخه حداکثر **یک** نود از هر pool گروه+منطقه shed
  می‌شود و ظرفیت باقی‌مانده هرگز زیرِ بارِ فعلی pool نمی‌افتد، تا یک منطقه روی یک نود گله نشود.
  `EDGE_CPU_SHED` (پیش‌فرض `0` = خاموش) سیگنال دومِ اختیاری است: `load1/cpus` در/بالای این مقدار برای
  همان تعداد گزارش هم shed می‌کند. shedding فقط روی DNS است و اتصال‌های تونلِ برقرار را قطع نمی‌کند.

- **بودجه‌ی خارج‌سازی مبتنی بر probe (F26) — `PROBE_WITHDRAW_MAX_FRACTION` (پیش‌فرض `0.34`).** یک
  vantage تکیِ کنترلر نباید همه‌ی نودها را از DNS بیرون بیندازد: این مقدار حداکثر کسری از آدرس‌های یک
  pool گروه+منطقه+خانواده را که صرفاً بر پایه‌ی probe می‌توان خارج کرد محدود می‌کند؛ فراتر از آن، بقیه
  آدرس‌ها آگهی می‌مانند و هشدار صادر می‌شود (یک «probe می‌گوید قطع است»ِ گسترده بیشتر نشانه‌ی vantageِ
  بد است تا مرگِ انبوهِ واقعی). خارج‌سازیِ یک آدرس پس از `PROBE_FAIL_CHECKS` (پیش‌فرض `3`) شکستِ پیاپی
  رخ می‌دهد و با اولین probe موفق برمی‌گردد؛ fail-open (بخش ۹ / SPEC §12.۳) همچنان مانع خالی‌شدنِ pool
  می‌شود.

- **probe اصلی به تفکیک خانواده (F32).** آدرس اصلی IPv4 و IPv6 اکنون وضعیت probe جدا دارند
  (`probe_ok4` / `probe_ok6`)؛ پس اگر فقط AAAA قطع باشد، رکورد AAAA خارج و رکورد A حفظ می‌شود (و
  برعکس)، به‌جای این‌که یک خانواده‌ی مرده کل نود را از آن خانواده بیرون بیندازد. آدرس‌های اضافی از پیش
  per-address بودند (بخش ۹). این تغییر تنظیم جدیدی ندارد.

- **پاسخ چند-نودی برای تونل (F33) — `TUNNEL_LUA_SELECTOR` (پیش‌فرض `all`).** سایت‌های تونل (با بخش
  `tunnel` فعال یا `edge_group=tunnel`) همه‌ی نودهای سالمِ pool را در پاسخ DNS می‌گیرند، تا یک dialer
  (مثل Go در Xray/sing-box) بی‌درنگ به آدرس بعدی failover کند و روی همان نود بماند (حفظ TLS
  resumption و کاهش جابه‌جایی). سایت‌های عمومی روی `LUA_SELECTOR` (پیش‌فرض `random`، تنها یک نود)
  می‌مانند.

- **fail-open تونل بدون GeoIP (F9).** اگر نود پایگاه‌داده‌ی GeoIP نداشته باشد، گیتِ
  `allowed_countries` روی مسیرهای تونل **اصلاً اعمال نمی‌شود** (fail-open) و یک `warning` در لاگ نود
  ثبت می‌شود، به‌جای این‌که همه‌ی کلاینت‌ها 403 بگیرند؛ heartbeat نود `geoip: true|false` را گزارش
  می‌کند و تایمر روزانه تا نصبِ پایگاه‌داده دوباره تلاش می‌کند. وقتی پایگاه‌داده هست، IPهایی که کشورشان
  ناشناخته است هم عبور می‌کنند. اگر برای مشتری‌ای اعمالِ سخت‌گیرانه لازم است، نودهای `geoip=false` را
  از پاسخ DNSِ آن سایت‌ها کنار بگذارید.

## ۱۱. قابلیت‌های موج ۶ روی نود (HTTP/3، Shield، mTLS، آمار زنده، ارسال لاگ)

همه‌ی موارد زیر با همان `--upgrade` روی نود می‌آیند و پیش‌فرضِ امن دارند؛ کاری لازم نیست مگر بخواهید
قابلیتی را روشن کنید.

| قابلیت | روی نود چه می‌شود | کار مدیر |
|---|---|---|
| **HTTP/3 (QUIC)** — اختیاری | با `--http3` به‌جای nginx توزیع، nginx mainline از مخزن رسمی nginx.org (کلید امضای pin‌شده) نصب می‌شود. ماژول geoip2/brotli در آن نیست؛ عامل خودش تشخیص می‌دهد (قوانین کشور fail-open، فقط gzip). | فقط اگر لازم دارید: `sudo ./install.sh --upgrade --http3` و **باز کردن UDP/443** در فایروال و security group (`ufw allow 443/udp`). برگشت: `--no-http3`. |
| **کنترل ازدحام TCP** | پیش‌فرض `bbr`. | در صورت نیاز `--cc cubic`. |
| **Origin Shield** | نودی که در پنل «Shield» آن روشن شده، لایه‌ی کش میانی سایت‌هایی می‌شود که گزینه‌ی Origin Shield را دارند (فقط برای سایت‌های دارای گواهی؛ مسیر نود→Shield همیشه TLS است). | در پنل مدیریت → نودها، کلید **Shield** را روی ۱ یا ۲ نود قوی روشن کنید. |
| **قوانین، WAF آماده، ربات‌ها** | `bots.conf` (فهرست IP خزنده‌های تأییدشده) فقط وقتی سایتی از مدیریت ربات استفاده کند ساخته می‌شود. | — |
| **احراز هویت مبدأ (mTLS)** | گواهی کلاینت در `/etc/nginx/pcdn/mtls/` (پوشه 0700، فایل‌ها 0600) فقط وقتی سایتی آن را فعال کند. | — |
| **آمار زنده + platform_errors** | آمار دقیقه‌ای همراه همان گزارش مصرف فرستاده می‌شود. | — |
| **ارسال لاگ (S3)** | برای سایت‌هایی که «ارسال لاگ» دارند، نمونه‌ای از لاگ دسترسی (IP ناشناس‌شده) در صف دیسکی کنار فایل وضعیت عامل (`/var/lib/pcdn/logship`، حداکثر ۲۵۶ مگابایت) جمع و به کنترلر فرستاده می‌شود. | اختیاری در `/etc/pcdn/agent.conf`: `LOGSHIP_SPOOL_MAX_MB`، `LOGSHIP_INTERVAL`، `LOGSHIP_TIMEOUT`، `LOGSHIP_SPOOL_DIR` (با `--upgrade` حفظ می‌شوند). |

پس از ارتقا، زیر نام هر نود در پنل مدیریت نشان‌های قابلیت دیده می‌شود: **HTTP/3**، **Early Hints**،
**WebP**، **آمار زنده** و **ارسال لاگ**. نودی که «آمار زنده» ندارد هنوز با عامل قدیمی کار می‌کند؛ آن را
`--upgrade` کنید.

> فرمت لاگ دسترسی nginx در این نسخه چند فیلد تازه گرفته است (`us`, `pg`, `sc`, `pr`, `rf`)؛ بنابراین هر نود
> پس از ارتقا **یک بار** nginx را reload می‌کند. خط‌های قدیمی لاگ همچنان خوانده می‌شوند.

## ۱۲. امکانات موج ۸ روی نود

| قابلیت | فعال‌سازی | نکته |
|---|---|---|
| پروکسی TCP/UDP | خودکار با `--upgrade` (ماژول stream + include در nginx.conf) | بازه‌ی `L4_PORT_RANGE` را برای TCP و UDP در فایروال باز کنید؛ فقط PROXY protocol v1 |
| ویدئو (HLS/DASH) | خودکار | برش ۱ مگابایتی mp4 با ماژول slice |
| تصاویر نسخه‌ی ۲ | خودکار؛ AVIF با `--avif` (بسته‌ی libavif-bin) | سرویس ایزوله‌ی `pcdn-imaged` روی loopback |
| محافظ شبکه | `--harden-net` / حذف با `--no-harden-net` | جدول nftables `pcdn_guard`؛ SSH و فهرست مجاز همیشه اول؛ تنظیمات `GUARD_*` در agent.conf |
| Edge Functions | `--functions` / حذف با `--no-functions` | سرویس `pcdn-fn` (QuickJS در سندباکس Landlock + seccomp)؛ وضعیت در `/run/pcdn-fn/status.json` |
| مبدأ باکت ذخیره‌سازی | خودکار | پورت داخلی `STORAGE_FETCH_PORT` (۸۰۹۱، فقط 127.0.0.1) |

بعد از ارتقا، زیر نام نود در پنل نشان‌های قابلیت تازه (`l4`، `video`، `avif`، `edge_functions`، …) گزارش
می‌شوند. اگر `l4` گزارش نشد، `sudo ./install.sh --upgrade` را دوباره اجرا کنید تا include ماژول stream اضافه شود.

عیب‌یابی سریع:
- `sudo nft list table inet pcdn_guard` — قوانین محافظ شبکه.
- `sudo systemctl status pcdn-fn pcdn-imaged` — سرویس‌های توابع و تصاویر.
- `sudo tail /var/log/nginx/pcdn-l4.log` — لاگ پروکسی TCP/UDP.


## ۱۳. موج ۱۳: تخلیه، پروب تونل، وزن DNS و HTTP/3 هر نود

جزئیات: `docs/SPEC.md` بخش ۲۲. هیچ‌کدام از این‌ها نودی را بر اساس «در دسترس بودن از شبکه‌ی کاربران» انتخاب
نمی‌کند؛ انتخاب نود همچنان فقط با سلامت، بار و ظرفیت خود نود است.

### ۱۳-۱. تخلیه (drain) پیش از ارتقا یا ری‌استارت

| وضعیت | معنا |
|---|---|
| `""` | عادی |
| `draining` | از همه‌ی پاسخ‌های DNS بیرون است؛ بعد از `PROXIED_TTL + 30` ثانیه اتصال تونلِ **تازه** (اولین درخواست هر اتصال) با 503 و `Retry-After: 30` رد می‌شود؛ نشست‌های موجود، استریم‌های تازه روی اتصال HTTP/2 موجود، POSTهای xhttp و ترافیک وب عادی دست نمی‌خورند |
| `drained` | اتصال‌های کلاینت به `DRAIN_IDLE_CONNS` (agent.conf، ۱۰) رسید یا زمان تخلیه تمام شد |

- قانون fail-open: اگر همه‌ی نودهای یک گروه+منطقه در حال تخلیه باشند، همه در DNS می‌مانند (استخر هرگز
  خالی نمی‌شود). شروع تخلیه‌ای که آخرین نود فعال (آنلاین، فعال، shed نشده، در حال تخلیه نه) گروه+منطقه را
  بیرون ببرد با 409 `last_edge` رد می‌شود؛ مدیر می‌تواند `force: true` بفرستد، خود نود نه.
- راه‌ها: پنل مدیر (منوی ردیف نود)، API (`POST|DELETE /api/v1/edges/{id}/drain`) یا روی نود:
  `sudo pcdn-agent drain --minutes 15 --wait` / `sudo pcdn-agent undrain`؛ در ارتقا:
  `bootstrap.sh --upgrade --drain[=دقیقه]` (پس از ارتقای موفق، نود خودش تخلیه را لغو می‌کند).
- تخلیه‌ی فراموش‌شده `DRAIN_MAX_HOLD_MINUTES` (۱۲۰) دقیقه بعد از پایان زمانش خودکار لغو می‌شود
  (هشدار `edge_drain_stuck:<id>`، رکورد ممیزی `edge.undrain` با عامل `system`).
- کنترلر همیشه وضعیت را نگه می‌دارد: حتی نود قدیمی که تخلیه را اجرا نمی‌کند، با تخلیه‌ی مدیر از DNS بیرون
  می‌رود (فقط اتصال تازه را رد نمی‌کند).

### ۱۳-۱-۱. حافظه‌ی نود، نسل‌های ورکر و محافظ حافظه

هر reload یک **نسل تازه‌ی ورکر** می‌سازد و نسل قبلی تا `worker_shutdown_timeout` (پیش‌فرض نصب: زیر ۴ گیگ
`30m`، ۴ تا ۸ گیگ `2h`، بالای ۸ گیگ `4h`) زنده می‌ماند تا نشست‌های تونلِ باز را نبندد. روی نود تونل که
نشست‌ها ساعت‌ها طول می‌کشند، چند reload پشت‌سر‌هم یعنی چند نسل همزمان در حافظه:

- عامل هر heartbeat `mem_pct` را گزارش می‌کند (در پنل، بخش معیارهای نود) و در `MEM_GUARD_PCT` (۹۲٪) قدیمی‌ترین
  ورکرِ در حال خاموشی را SIGTERM می‌کند — هرگز مستر و هرگز ورکر نسل جاری.
- از `MEM_GUARD_HARD_PCT` (۹۷٪) به بالا «حالت بحرانی»: همان heartbeat اول اقدام می‌کند، تا
  `MEM_GUARD_MAX_KILLS` (۳) نسل را یکجا می‌بندد، و ورکری که `MEM_GUARD_KILL_GRACE_S` (۶۰ ثانیه) بعد از
  SIGTERM هنوز نرفته باشد SIGKILL می‌شود. همچنین تا وقتی نسلی در حال تخلیه است، reload تا سقف ۶۰۰ ثانیه عقب
  می‌افتد (`RELOAD_MAX_WAIT` در نهایت آن را اعمال می‌کند).
- چرا این‌قدر مهم است: اگر کار به OOM killer کرنل برسد، قربانی را کرنل انتخاب می‌کند و می‌تواند **مستر nginx**
  باشد؛ آن وقت همهٔ تونل‌های نود با آن می‌روند و `/run/nginx.pid` خالی می‌ماند — یعنی همان حالتی که دیگر هیچ
  reloadای کار نمی‌کند (ردیف مربوطه در جدول عیب‌یابی).
- اگر روی نودی `mem_pct` مرتب بالای ۹۰٪ است: RAM را بالا ببرید، یا با `install.sh --shutdown-timeout 30m`
  عمر نسل‌های قدیمی را کوتاه کنید، یا `RELOAD_MIN_INTERVAL` را بالا ببرید (کمتر reload)، و ظرفیت
  (`capacity_mbps`) نود را واقع‌بینانه تنظیم کنید تا بار روی نودهای دیگر پخش شود.

### ۱۳-۲. پروب داخلی تونل و حالت «خراب»

عامل نود هر `PROBE_INTERVAL` (۶۰ ثانیه) از طریق loopback یک نشست WS (و در صورت امکان gRPC) را از nginx،
TLS و مسیر پروکسی تونل **خود نود** عبور می‌دهد (مبدأ اکوی محلی یا `TUNNEL_PROBE_ORIGIN` اپراتور؛ هرگز
مبدأ مشتری). کنترلر هر گزارش تازه را یک بار می‌شمارد:
- `TUNNEL_PROBE_FAIL_CHECKS` (۳) گزارش ناموفق پیاپی ← نود «خراب تونل» (`tunnel_degraded`)، هشدار
  `edge_tunnel_degraded:<id>` و رکورد `degraded` در `edge_events`.
- `TUNNEL_PROBE_OK_CHECKS` (۵) گزارش موفق **و** دست‌کم ۱۰ دقیقه در حالت خراب ← بازگشت (`recovered`).
- اثر DNS فقط روی **سایت‌های تونل**: در هر استخر گروه+منطقه حداکثر `floor(n × TUNNEL_DEGRADED_MAX_FRACTION)`
  نود (پیش‌فرض نصف) کنار می‌رود — قدیمی‌ترین خرابی اول، تازه‌ترین‌ها می‌مانند — و استخر هرگز خالی نمی‌شود.
  سایت‌های وب عادی نود را نگه می‌دارند. نودی که پروب نمی‌فرستد (عامل قدیمی) هرگز خراب علامت نمی‌خورد.

### ۱۳-۳. وزن پاسخ‌های DNS (`DNS_WEIGHTS=capacity`)

پیش‌فرض `off` است و زون‌ها دقیقاً مثل قبل‌اند. با `capacity` هر نود در استخر خودش (گروه + منطقه + IPv4/IPv6)
وزن `q` از ۱ تا ۴ می‌گیرد: پایه = `capacity_mbps` (برای ظرفیت ناشناخته، میانه‌ی ظرفیت‌های معلوم استخر یا ۱۰۰)
× ضریب بار (سطح ۰ = ۱، سطح ۱ = ۰٫۵ در ≥ ۷۰٪، سطح ۲ = ۰٫۲۵ در ≥ ۸۵٪؛ بالا رفتن با ۲ گزارش پیاپی، پایین آمدن
زیر ۶۰٪ / ۷۵٪ با ۳ گزارش). وزن فقط روی انتخاب‌گرهای `random` (`pickwrandom`) و `hashed` (`pickwhashed`)
اثر دارد (با `EDGE_PROBE` فهرست ifurlup هر آدرس را `q` بار تکرار می‌کند). سایت‌های تونل
(`TUNNEL_LUA_SELECTOR=all`) همچنان **همه‌ی** نودهای سالم را می‌گیرند — پاسخ هرگز کوتاه یا نمونه‌گیری نمی‌شود.
`shed` (`EDGE_SHED_PERCENT`) همچنان نود را کامل بیرون می‌برد. وزن هر نود در پنل (`dns_weight`) دیده می‌شود.

### ۱۳-۴. HTTP/3 هر نود و کلیدهای TLS

- کلید «HTTP/3» هر نود (`PATCH /api/v1/edges/{id}` با `http3_enabled`): QUIC فقط وقتی روی نود ساخته می‌شود
  که nginx آن را پشتیبانی کند **و** این کلید روشن باشد. پورت UDP همان پورت HTTPS را در فایروال باز کنید.
  پنل مشتری نسخه‌ی HTTP/3 لینک xhttp را فقط وقتی نشان می‌دهد که **همه‌ی** نودهای آنلاینِ سرویس HTTP/3
  داشته باشند.
- `TLS_TICKETS=on` (با `DATA_ENCRYPTION_KEY`): کلیدهای مشترک session ticket بین همه‌ی نودها؛ هر
  `TLS_TICKET_ROTATE_HOURS` (۲۴) یک بار می‌چرخند و هر چرخش یک reload روی نودها است. ملاحظات امنیتی:
  `docs/SECURITY.md`.
- `ACME_DUAL_RSA=true`: کنار گواهی ECDSA یک گواهی RSA-2048 هم صادر و سرو می‌شود (برای کلاینت‌های قدیمی).

### ۱۳-۵. گزارش‌های تازه‌ی هر نود در پنل

بارگذاری مجدد nginx در ساعت/۲۴ ساعت، نسل‌های کارگرِ در حال خاموش شدن (`draining_workers`)، مهلت خاموشی
کارگرها (WST)، سوکت‌های TCP / TIME_WAIT، نتیجه‌ی پروب تونل (setup ms، سرعت دانلود/آپلود، آخرین خطا) و
بررسی تنظیمات هسته (sysctl، qdisc، nofile). هشدارها در `docs/MONITORING.md`.

## ۱۴. موج ۱۴: شهر نمایشی، برچسب عمومی، نسخهٔ پین‌شده و توکن پیوستن (SPEC §23)

- **شهر نمایشی:** مشتری هرگز نام داخلی نود را نمی‌بیند؛ به‌جای آن «نود تهران» / "Tehran node" (با شماره‌گذاری
  «نود تهران ۱»، «نود تهران ۲» وقتی چند نود یک شهر دارند؛ شماره‌ها به ترتیب شناسه و روی همهٔ نودها، فعال یا
  غیرفعال، تا با غیرفعال‌شدن یکی جابه‌جا نشوند). تنظیم:
  `curl -X PATCH -H "Authorization: Bearer $ADMIN_API_KEY" -d '{"display_city": "تهران"}' $C/api/v1/edges/3`
  (`display_city_en` اختیاری؛ نام انگلیسی شهرهای رایج از `controller/app/data/cities.json`؛ `""` پاک می‌کند؛
  بدون شهر: «ایران» برای home و «بین‌المللی» برای global).
- **برچسب عمومی:** هر نود یک `public_tag` هشت‌هگزی پایدار دارد که در `X-Served-By` و `X-Pcdn-Node` فرستاده
  می‌شود (پس از ارتقای نود؛ نودهای قدیمی تا ارتقا نام میزبان را می‌فرستند). برای یافتن نودِ یک سرآیند مشتری:
  `GET /api/v1/edges?tag=<tag>`.
- **نسخهٔ پین‌شده:** با `EDGE_RELEASES_DIR` و `EDGE_RELEASE` (یا پایان یک rollout) دستور نصب `--version vX.Y.Z`
  می‌گیرد و bootstrap بستهٔ همان نسخه را با sha256 بررسی می‌کند. ستون «نسخه» در پنل `release` نود را با نسخهٔ
  پین‌شدهٔ گروه مقایسه می‌کند. ارتقای نودها: صفحهٔ «انتشار نسخه» (docs/OPERATIONS.md §۱۰).
- **توکن پیوستن:** برای نودی که هنوز وصل نشده `POST /api/v1/edges/{id}/join-token` یک توکن یک‌بارمصرف
  (`JOIN_TOKEN_HOURS`) و دستور نصب با `PCDN_JOIN_TOKEN` می‌دهد؛ نصب‌کننده با `POST /edge/v1/join` توکن دائمی
  نود را دریافت می‌کند. نودهای پیشنهادهای provisioning همین مسیر را می‌روند.
