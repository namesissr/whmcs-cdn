## ۱. مدیریت اسرار

همهٔ اسرار در فایل `.env` روی سرور کنترلر زندگی می‌کنند. این فایل:

- **هرگز در git نباشد** (در `.gitignore` است) و دسترسی فایل‌سیستمی‌اش محدود باشد (`chmod 600`).
- در پشتیبان بدون‌رمز قرار نگیرد؛ به‌خصوص `DATA_ENCRYPTION_KEY` و `BACKUP_PASSPHRASE` باید
  **بیرون از سرور** (مدیر رمز/خزانه) هم کپی داشته باشند، وگرنه بازیابی ناممکن است
  (نگاه کنید به [`docs/DISASTER_RECOVERY.md`](DISASTER_RECOVERY.md)).

اسرار کلیدی و منبعشان:

| راز | تنظیم | کاربرد | نحوهٔ تولید |
|---|---|---|---|
| کلید ادمین | `ADMIN_API_KEY` | احراز WHMCS و همهٔ `/api/v1/*` | `openssl rand -hex 32` |
| کلید API مشتری | (خودکار) | هر سرویس، `/capi/v1/*` | کنترلر می‌سازد (`pcdn_` + ۴۰ hex)؛ فقط هش ذخیره می‌شود |
| کلید PowerDNS | `PDNS_API_KEY` | نوشتن زون‌ها روی هر نیم‌سرور | `openssl rand -hex 24` |
| کلید رمزنگاری دیتابیس | `DATA_ENCRYPTION_KEY` | رمزنگاری کلید خصوصی گواهی‌ها و secret سایت‌ها | `manage gen-key` |
| رمز پشتیبان | `BACKUP_PASSPHRASE` | رمزنگاری آرشیو پشتیبان (AES-256-GCM) | یک رمز قوی و یکتا |
| رمز دیتابیس | `POSTGRES_PASSWORD` | PostgreSQL | رمز قوی |
| توکن متریک | `METRICS_TOKEN` | محافظت `GET /metrics` (SPEC §13.1) | `openssl rand -hex 32` |
| اسرار هشدار | `TELEGRAM_BOT_TOKEN`، `SMTP_PASSWORD`، `BACKUP_S3_SECRET_KEY` | کانال‌های هشدار و ابری | — |

نکتهٔ مهم: کلید ادمین به‌صورت **ثابت‌زمانی** مقایسه می‌شود (`hmac.compare_digest`)، توکن نودها و کلید
مشتری فقط به‌صورت **هش SHA-256** ذخیره می‌شوند و قابل بازیابی نیستند، و کلید خصوصی گواهی‌ها در دیتابیس
رمزنگاری‌شده‌اند. اگر `ADMIN_API_KEY` تنظیم نشده باشد، هیچ درخواست ادمینی پذیرفته نمی‌شود.

## ۲. در معرض قرار گرفتن شبکه (پورت‌ها)

قاعدهٔ کلی: فقط چیزی که باید عمومی باشد را عمومی کنید.

| پورت | جزء | باید باشد | توضیح |
|---|---|---|---|
| `53/udp`, `53/tcp` | PowerDNS | **عمومی** | پاسخ DNS معتبر — ناگزیر عمومی |
| `80`, `443` | Caddy | **عمومی** | API کنترلر پشت TLS؛ `80` فقط برای چالش ACME |
| `80`, `443` | نودهای Edge | **عمومی** | سرو سایت‌ها و تونل‌ها |
| `8000` | Controller | **داخلی** | روی هاست منتشر نمی‌شود؛ فقط Caddy می‌رسد |
| `8081` | PowerDNS API | **داخلی/scrape** | روی تک‌سرور منتشر نمی‌شود |
| `5432` | PostgreSQL | **داخلی** | روی هاست منتشر نمی‌شود |

هشدارهای مهم:

- **`ufw` از پورت‌هایی که Docker منتشر می‌کند محافظت نمی‌کند.** روی `ns2` که API PowerDNS را روی
  `8081` منتشر می‌کند، باید با `sudo ./deploy/ns2-firewall.sh <controller-ip>` پورت ۸۰۸۱ را فقط به
  IP کنترلر محدود کنید. در حالت HA هم `5432` و `8081` فقط به IP خصوصی سرور دیگر باز شوند.
- **API PowerDNS و دیتابیس هرگز نباید روی اینترنت عمومی باز باشند.** `webserver-allow-from` در
  `dns/pdns.conf` فقط loopback و شبکه‌های خصوصی (`10/8`، `172.16/12`، `192.168/16`، `fc00::/7`) است و
  `docker-compose.yml` آن را از `PDNS_API_ALLOW_FROM` روی خط فرمان pdns تنظیم می‌کند. ns2 جدا را از
  **شبکهٔ خصوصی** (WireGuard / شبکهٔ خصوصی دیتاسنتر) یا **https** به کنترلر وصل کنید (بخش ۱۰، M5).
- **پورت `80` نودها** باید برای کنترلر و PowerDNS باز بماند تا پروب سلامت
  (`http://<node>/__pcdn/health`، Host: `health.pcdn`) کار کند.
- `/metrics` فقط روی یک شبکهٔ scrape داخلی یا پشت `METRICS_TOKEN` در دسترس باشد (بخش ۹).

## ۳. TLS

- گواهی `CONTROLLER_DOMAIN` را Caddy خودکار از Let's Encrypt می‌گیرد و تمدید می‌کند
  (`deploy/Caddyfile`).
- گواهی سایت‌های مشتری با acme.sh و روش DNS-01 صادر می‌شوند (`ACME_EMAIL`، `ACME_SERVER`)؛ کنترلر
  آن‌ها را خودکار تمدید می‌کند (`job_ssl`) و اگر گواهی تا `ALERT_CERT_DAYS` (پیش‌فرض ۷) روز منقضی شود
  هشدار می‌دهد.
- روی نودها، حداقل نسخهٔ TLS در njs اعمال می‌شود (در nginx 1.24 تنظیم per-domain کار نمی‌کند): درخواست
  با TLS پایین‌تر رد می‌شود.
- WHMCS باید فقط از طریق HTTPS با کنترلر حرف بزند (آدرس = `CONTROLLER_DOMAIN`).

## ۴. چرخش توکن‌ها و کلیدها

- **توکن نود (edge):** از پنل WHMCS یا `POST /api/v1/edges/{id}/rotate-token`. توکن جدید یک‌بار نشان
  داده می‌شود؛ نود را با `--upgrade` یا با به‌روزرسانی `/etc/pcdn/agent.conf` به توکن جدید تنظیم کنید.
  توکن قدیمی بی‌اثر می‌شود (فقط هش ذخیره شده بود).
- **کلید API مشتری:** از ناحیهٔ کاربری/ماژول WHMCS دوباره صادر می‌شود؛ هر کلید به یک سرویس و زیرمجموعه‌ای
  از دامنه‌های `{purge, stats, dns}` محدود است.
- **کلید ادمین (`ADMIN_API_KEY`):** مقدار جدید در `.env` بگذارید، کنترلر را ری‌استارت کنید و همان
  مقدار را در «Access Hash» سرور WHMCS به‌روز کنید. چون ثابت‌زمانی مقایسه می‌شود، صرفاً تعویض مقدار کافی است.
- **کلید رمزنگاری (`DATA_ENCRYPTION_KEY`):** چرخش بدون قطعی با گذاشتن کلید جدید اول، `manage rotate-key`
  و سپس حذف کلید قدیمی (DR §۴).
- **کلید PowerDNS (`PDNS_API_KEY`):** روی همهٔ نیم‌سرورها و کنترلر هم‌زمان ست و سپس `dns-sync` (DR §۵).

## ۵. حداقل دسترسی (least privilege)

- هر سطح احراز هویت فقط به کار خودش دسترسی دارد: نود فقط `/edge/v1/*`، مشتری فقط `/capi/v1/*` و تنها
  سایت خودش با دامنه‌های محدود، WHMCS با کلید ادمین به `/api/v1/*`.
- API مشتری علاوه بر `CAPI_RATE` (پیش‌فرض ۶۰/دقیقه) یک محدودیت تنگ‌تر برای *نوشتن* کانفیگ/رکورد دارد
  (`CAPI_CONFIG_RATE`، پیش‌فرض ۶/دقیقه) تا یک کلاینت نتواند با رگبار تغییرات، کل ناوگان را به reload
  وادار کند.
- روی نود، عامل با کاربر غیرویژه (`NGINX_USER=www-data` برای nginx) کار می‌کند و کلید خصوصی گواهی‌ها
  با دسترسی `600` نوشته می‌شوند.
- ورودی‌ها در کنترلر اعتبارسنجی می‌شوند؛ مثلاً IP خصوصی یا loopback به‌عنوان Origin پذیرفته نمی‌شود، و
  عامل هم پیش از نوشتن کانفیگ nginx، نام‌ها و Originها را دوباره بررسی می‌کند.
- دسترسی SSH سرورها و فایل `.env` را به حداقل افراد محدود کنید.

## ۶. پشتیبان‌های off-box

- پشتیبان‌گیری روزانه را روشن نگه دارید (`BACKUP_ENABLED=true`، ساعت `BACKUP_HOUR` به UTC).
- آرشیو را **رمزنگاری** کنید (`BACKUP_PASSPHRASE`؛ AES-256-GCM). بدون آن، آرشیو در صورت افشا
  قابل‌خواندن است.
- آرشیو را **بیرون از سرور** نگه دارید (`BACKUP_S3_*`، مثلاً Object Storage آروان با path-style و
  SigV4). کلید `BACKUP_S3_SECRET_KEY` را مثل بقیهٔ اسرار محافظت کنید.
- `BACKUP_KEEP` (و `BACKUP_S3_KEEP`) تعداد نسخه‌های نگه‌داشته‌شده را تعیین می‌کنند.
- قابل‌بازیابی بودن پشتیبان را دوره‌ای بیازمایید (DR §۷، `manage backup-verify`).

## ۷. رمزنگاری در حال سکون

- کلید خصوصی گواهی‌ها (`Site.ssl_key_stored`) و secret هر سایت (`Site.secret_stored`) با
  `DATA_ENCRYPTION_KEY` (Fernet) رمزنگاری می‌شوند (`controller/app/crypto.py`). مقدار به‌صورت
  `enc:v1:<token>` ذخیره می‌شود.
- اگر `DATA_ENCRYPTION_KEY` تنظیم نباشد، این داده‌ها **plaintext** ذخیره می‌شوند و کنترلر در لاگ
  شروع و در `/healthz/deep` هشدار می‌دهد. برای رمزنگاری دادهٔ موجود: `manage encrypt-secrets` (در
  شروع هم خودکار اجرا می‌شود). وضعیت را با `manage encryption-status` ببینید.
- در حالت HA هر دو سرور باید **دقیقاً همان** `DATA_ENCRYPTION_KEY` را داشته باشند.
- توکن نودها و کلیدهای مشتری اصلاً plaintext ذخیره نمی‌شوند؛ فقط هش SHA-256 (غیرقابل‌بازگشت).

## ۸. لاگ حسابرسی (SPEC §13.2)

برای پاسخگویی (accountability)، هر **تغییرِ** (write) ادمین و API مشتری در جدول `audit_log` ثبت
می‌شود: `actor` (برچسب کلید ادمین / شناسهٔ کلید مشتری / `system`)، `actor_kind` (`admin|capi|system`)،
`action` (مثل `site.create`، `site.plan`، `site.delete`، `edge.add`، `edge.rotate`، `edge.patch`،
`edge.delete`، `edge.address.add/del`، `purge`، `reseller.flag`، `reseller.rate`،
`tunnel.enable_existing`)، `target`، `detail` (JSON، **بدون هیچ راز/توکن/کلید خصوصی**) و `ip`.
خواندن‌ها ثبت نمی‌شوند. `GET /api/v1/audit?limit=&since=&action=&actor=` (ادمین) تازه‌ترین‌ها را
برمی‌گرداند، و یک کار زمان‌بند ردیف‌های قدیمی‌تر از `AUDIT_RETENTION_DAYS` (پیش‌فرض ۹۰) را هرس می‌کند.

> لاگ حسابرسی در موج ۵ طبق SPEC §13.2 در حال پیاده‌سازی است. در WHMCS یک صفحهٔ «حسابرسی» آن را با
> فیلتر (action/actor/time) نشان می‌دهد.

## ۹. مشاهده‌پذیری و متریک‌ها (SPEC §13.1)

- `GET /metrics` فقط **شمارنده‌های کل پلتفرم** را به فرمت Prometheus می‌دهد (تعداد نودها/سایت‌ها،
  وضعیت SSL و گواهی‌های نزدیک انقضا، سن آخرین sync DNS، سن آخرین اجرای هر کار زمان‌بند، سن آخرین
  پشتیبان موفق، ...). **هیچ** دامنه/IP/توکنی لو نمی‌دهد.
- احراز: اگر `METRICS_TOKEN` تنظیم باشد، `Authorization: Bearer <token>` لازم است؛ وگرنه endpoint
  باز است و باید فقط روی یک شبکهٔ scrape داخلی قرار بگیرد.
- `GET /healthz/deep` (کلید ادمین) هم گزارش کامل سلامت بدون راز می‌دهد و برای مانیتور/پروب مناسب است.

## ۱۰. بازبینی امنیتی موج ۹ (کنترلر)

خلاصهٔ رفتار پس از رفع یافته‌های بازبینی امنیتی؛ هر بند تست رگرسیون در
`controller/tests/test_security_w9.py` دارد.

### C1 — زیردامنهٔ مشتری دیگر (sub-zone takeover)

همهٔ زون‌ها روی نیم‌سرورهای ما هستند و PowerDNS از **دقیق‌ترین** زون پاسخ می‌دهد؛ پس سایتی مثل
`shop.victim.com` از حساب دیگری، رکوردهای `victim.com` را برای آن نام از کار می‌انداخت.

- **مالک** سایت: `client_id` (شناسهٔ مشتری WHMCS، در `POST /api/v1/sites` فرستاده می‌شود) وگرنه
  `reseller_client_id` (زیرسایت نماینده متعلق به نماینده است). سایت بدون هر دو «بی‌مالک» است و با هیچ
  سایتی هم‌مالک حساب نمی‌شود. `PATCH /api/v1/sites/{domain}/owner` مالک را تنظیم می‌کند.
- ساخت سایتی که والد یا فرزند (در هر عمق) سایتی با **مالک دیگر** باشد ← `422`. تکراری دقیق همچنان `409`.
- **پسوند عمومی** (`com`، `co.ir`، `ac.ir`، `gov.ir`، `org.ir`، `net.ir`، `sch.ir`، `id.ir`، `co.uk` …) هرگز
  سایت نمی‌شود ← `422`. پیش‌بررسی برای سبد خرید WHMCS: `POST /api/v1/domain-check`
  (`{domain, client_id?, reseller_client_id?}` ← `{ok, code: invalid|public_suffix|exists|nested, error}`).
- فهرست پسوندها: بخش ICANN از Public Suffix List در `controller/app/data/public_suffix_list.dat`؛ پسوندهای
  ایرانی همیشه در کد هم هستند. به‌روزرسانی (هر چند ماه یک بار):
  `curl -fsSLo /tmp/psl.dat https://publicsuffix.org/list/public_suffix_list.dat && python -m app.psl /tmp/psl.dat`
  (در پوشهٔ `controller/`) و commit فایل.
- **بررسی NS**: علاوه بر پاسخ resolver (`NS_RESOLVERS`)، (۱) اگر سایت والدی با مالک دیگر وجود داشته باشد فعال
  نمی‌شود؛ (۲) با `NS_CHECK_PARENT=true` (پیش‌فرض) از سرورهای پسوند عمومی به پایین (بدون recursion، با دنبال
  کردن referralها) بررسی می‌شود که **زون والد ثبت‌شده** دقیقاً همین نام را به نیم‌سرورهای ما واگذار کرده
  باشد؛ اگر referral زودتر برای یک نام والد به نیم‌سرورهای ما برسد، فقط وقتی پذیرفته است که آن والد سایتِ
  همان مالک باشد. اگر سرورهای والد در دسترس نباشند این گام با هشدار لاگ رد می‌شود (قاعدهٔ (۱) همیشه برقرار
  است). پاسخ `ns-check` فیلد `reason` دارد (`nameservers` | `parent_delegation` | `parent_site:<domain>`).
- جفت‌های تودرتوی قدیمی با مالک متفاوت: هشدار `nested_sites` (کار زمان‌بندی‌شدهٔ رهبر).

### H1 — DNS ثانویه و رکوردهای LUA

- بخش `dns_secondary` اکنون قابلیت پلن `dns_secondary` است (پیش‌فرض **خاموش**). پیکربندی ذخیره‌شدهٔ
  پیشین دست نمی‌خورد؛ برای پلن‌هایی که آن را می‌فروشند قابلیت را روشن کنید.
- هر زون Slave (محتوای آن از سرور اصلی مشتری می‌آید) متادیتای `ENABLE-LUA-RECORDS=0` می‌گیرد — در هر
  همگام‌سازی و پیش از تغییر نوع/انتقال، پس زون‌های قدیمی هم اصلاح می‌شوند. زونی که Native می‌شود فقط پس از
  جایگزینی رکوردهایش توسط کنترلر دوباره LUA می‌گیرد. زون‌های Native تماماً نوشتهٔ کنترلرند و مشتری نوع
  LUA نمی‌تواند بسازد. (گام بعدی اختیاری: `enable-lua-records=no` سراسری + متادیتای `1` روی زون‌های Native؛
  فعلاً انجام نشده چون تا پر شدن متادیتای همهٔ زون‌ها، پاسخ رکوردهای پروکسی قطع می‌شد.)
- آدرس `primaries` / `allow_axfr` باید عمومی باشد (همان قاعدهٔ `netguard`، شامل CGNAT).
- **L2:** نام کلید TSIG باید زیر دامنهٔ همان سرویس باشد (`transfer.example.com`)؛ نام ذخیره‌شدهٔ قبلی
  حفظ می‌شود.

### H2 — عبارت‌های منظم مشتری

همهٔ فیلدهای regex مشتری از یک بررسی‌کننده (`sections._safe_regex`: حداکثر ۲۵۶ کاراکتر، بدون تکرار تودرتو یا
گزینه‌های هم‌پوشان، حداکثر ۱۰ کمیت‌سنج نامحدود) می‌گذرند: شرط `regex` فایروال، `rewrite_path` تبدیل و
ریدایرکت regex. بقیهٔ فیلدهای مسیر (page rule، rate limit، WAF exclusion، تبدیل) الگوی glob هستند، نه
regex. قانون فایروالی که پیش از این بررسی ذخیره شده و ناامن است در پیکربندی لبه فرستاده **نمی‌شود** (فقط
همان قانون؛ بقیه می‌مانند).

### M1 — گزارش مصرف لبه

- هر لبه فقط برای سایت‌های **گروه خودش** مصرف/رویداد/آمار زنده گزارش می‌دهد (مصرف لبهٔ گروه دیگر در حالت
  fail-open حساب نمی‌شود).
- سقف ساعتی هر لبه (جمع همهٔ سایت‌ها): `capacity_mbps × 3600 / 8 × USAGE_SAFETY_FACTOR` بایت (بدون ظرفیت:
  `USAGE_MAX_GBPS`) و `USAGE_MAX_RPS × 3600` درخواست؛ ساعت آینده یا قدیمی‌تر از `USAGE_MAX_AGE_DAYS`
  دور ریخته می‌شود. موارد ردشده اعمال نمی‌شوند، در پاسخ (`dropped`) و متریک `metrics:usage_dropped` شمرده
  و هشدار `usage_implausible:<edge id>` باز می‌شود.

### M2 / M3 — کلیدهای API مشتری

| دسترسی | چه چیزی |
|---|---|
| `purge` | پاک‌سازی کش |
| `stats` | آمار، رویدادها، گزارش تونل، آمار توابع (فقط خواندن) |
| `dns` | رکوردهای DNS و بخش `dns_secondary` |
| `config` | سایر بخش‌های پیکربندی، ورود CSV ریدایرکت، کلید امضای تصویر |
| `functions` | بخش `functions` (کد توابع لبه) |

کلیدهای موجودِ دارای `dns` در مهاجرت `0019` دسترسی `config` هم گرفتند (همان کاری که قبلاً می‌توانستند)
اما **نه** `functions`. وقتی سرویس معلق است، کلیدها فقط **می‌خوانند**؛ هر نوشتن (purge، رکورد، پیکربندی،
کلید تصویر) `403` است. (`over_quota` نوشتن را نمی‌بندد تا مشتری بتواند مثلاً کش را روشن کند.)

### مبدأهای مشتری (origin)

لبه‌ها به مبدأ رکوردهای پروکسی‌شده (A/AAAA/CNAME)، اعضای استخر، مبدأ مسیرهای تونل و مبدأ برنامه‌های
L4 وصل می‌شوند (مبدأ فضای ذخیره‌سازی ساختهٔ پلتفرم است و شامل نیست). **قاعده** (کنترلر هنگام ذخیره،
بازبینی دوره‌ای، و لبه هنگام اتصال):

1. آدرس IP باید عمومیِ قابل‌مسیریابی باشد (`netguard.is_public_ip`): نه خصوصی (`10/8`، `172.16/12`،
   `192.168/16`، `fc00::/7`)، loopback، link-local (`169.254/16`، `fe80::/10`)، CGNAT (`100.64/10`)،
   نامشخص، multicast، رزروشده/مستندسازی/benchmark، site-local، و نه IPv6ای که IPv4 غیرعمومی را در خود دارد
   (`::ffff:0:0/96`، 6to4 `2002::/16`، Teredo، NAT64 `64:ff9b::/96` و `64:ff9b:1::/48`).
2. نام میزبان باید کامل باشد (دست‌کم دو برچسب)، برچسب آخرش حرفی یا `xn--` باشد (نه عددی/hex مثل
   `0x7f.1`) و زیر نام‌های ویژه/داخلی نباشد: `localhost`، `localdomain`، `local`، `internal`، `intranet`،
   `lan`، `home`، `corp`، `private`، `arpa`، `test`، `invalid`، `onion`، `alt`، `example`.
3. هنگام ذخیره نام resolve می‌شود (A و AAAA)؛ اگر **هر** آدرسش غیرعمومی باشد ← `422` با پیام روشن. نامی که
   (هنوز) resolve نمی‌شود پذیرفته می‌شود. CNAME درون همان زون از رکوردهای خود زون دنبال می‌شود. رکورد
   غیرپروکسی بررسی نمی‌شود (لبه به آن وصل نمی‌شود).
4. رهبر زمان‌بند هر `ORIGIN_RECHECK_MINUTES` دقیقه همهٔ مبدأها را دوباره resolve می‌کند؛ مبدئی که اکنون به
   آدرس غیرعمومی اشاره کند در فهرست مسدود (`State: origin_guard:blocked`) می‌رود: میزبان/عضو استخر/مسیر
   تونل/برنامهٔ L4 مربوط از پیکربندی لبه حذف و هشدار `origin_guard` باز می‌شود؛ با عمومی شدن دوباره خودکار
   برمی‌گردد.
5. **لبه** باید همین قاعده را هنگام اتصال اجرا کند (آدرس resolveشده را بررسی و به همان آدرس وصل شود)،
   چون بین بررسی کنترلر و اتصال، DNS می‌تواند تغییر کند.

### M4 — گواهی کلاینت مشترک origin-pull

گواهی کلاینت حالت `platform` بین همهٔ مستأجرها مشترک است: مبدئی که به CA پلتفرم اعتماد کند، درخواست لبه
برای **هر** سایتی را می‌پذیرد (مشتری دیگری می‌تواند سایت خودش را به همان مبدأ اشاره دهد). برای جداسازی از
حالت `custom` (گواهی اختصاصی هر سایت) استفاده کنید یا در مبدأ علاوه بر گواهی، `Host`/SNI را هم بررسی کنید.

### M5 — API PowerDNS

- `webserver-allow-from` فقط loopback و شبکه‌های خصوصی (قابل تغییر با `PDNS_API_ALLOW_FROM` در
  `docker-compose.yml`).
- ns2 جدا: API را فقط روی شبکهٔ خصوصی (WireGuard) یا پشت https در دسترس کنترلر بگذارید؛ در compose آن هم
  `command: ["--webserver-allow-from=<IP خصوصی کنترلر>/32"]` بدهید. **توجه:** چون `dns/pdns.conf` مشترک است،
  ns2ای که از IP عمومی کنترلر صدا زده می‌شد پس از به‌روزرسانی API را رد می‌کند تا این تنظیم انجام شود.
- کنترلر هنگام شروع و در هشدار `pdns_insecure` آدرس‌های `http://` به آدرس عمومی/نام دامنه در
  `PDNS_API_URL` را گزارش می‌کند؛ `PDNS_API_REQUIRE_PRIVATE=true` شروع کنترلر را در این حالت متوقف می‌کند.

### M6 — اسرار در پیکربندی همهٔ لبه‌ها (مستند، پیاده نشده)

هر لبه پیکربندی **همهٔ** سایت‌ها را می‌گیرد: گواهی و کلید خصوصی TLS، `secret` سایت (کوکی چالش)، توکن خواندن
باکت ذخیره‌سازی، جفت گواهی/کلید origin-pull اختصاصی، کلید امضای تصویر، کلید `X-Pcdn-Shield` ناوگان و کلید
کلاینت پلتفرم. محدود کردن به سایت‌های گروه خود لبه **امن نیست**: در DNS fail-open (`dnsbuild.dns_edges`:
وقتی گروه یک سایت هیچ لبهٔ آنلاینی ندارد همهٔ لبه‌ها پاسخ می‌دهند) لبهٔ گروه دیگر باید همان لحظه گواهی و
کلید سایت را داشته باشد؛ فاصلهٔ poll پیکربندی از TTL پاسخ DNS بیشتر است و قطع گروه به قطع HTTPS تبدیل
می‌شد. پس یک لبهٔ نفوذشده همهٔ مستأجرها را افشا می‌کند. کاهش ریسک: لبه‌ها را مثل سرورهای حساس سخت کنید،
توکن لبهٔ مشکوک را فوراً `rotate-token`/غیرفعال و همهٔ گواهی‌ها را دوباره صادر کنید. راه بلندمدت: دریافت
کلید به‌ازای هر سایت هنگام نیاز یا keyless/HSM.

### L3 / L4

- uvicorn هدرهای پروکسی را فقط از `FORWARDED_ALLOW_IPS` (پیش‌فرض loopback و شبکه‌های خصوصی) می‌پذیرد، نه `*`.
- محدودیت نرخ API مشتری (`CAPI_RATE`، `CAPI_CONFIG_RATE`) در حافظهٔ هر پردازه است؛ با N کنترلر سقف
  مؤثر N برابر است. فعلاً مستند شده (شمارندهٔ مشترک در دیتابیس به ازای هر درخواست هزینهٔ نوشتن دارد).
