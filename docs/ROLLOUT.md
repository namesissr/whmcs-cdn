# استقرار تدریجی در محیط واقعی (Rollout) — CDN پاسارگاد

این راهنما مسیر بردن یک نسخهٔ تازه (مثلاً `v2.0.0`) از مخزن به محیط واقعی است: staging ← یک نود
آزمایشی (canary) و مشتریان داخلی به مدت یک هفته ← همهٔ نودها و مشتریان. قرارداد این بخش در
[SPEC §18.6](SPEC.md) است؛ گام‌های فنی هر جزء در [UPGRADE.md](UPGRADE.md)
و بازیابی در [DISASTER_RECOVERY.md](DISASTER_RECOVERY.md) آمده‌اند. تغییرات هر نسخه در
[CHANGELOG.md](../CHANGELOG.md) ثبت می‌شود.

## ۱. نمای کلی مراحل

| مرحله | کجا | مدت | خروج از مرحله |
|---|---|---|---|
| ۰. آماده‌سازی | مخزن | — | CI روی `main` سبز، `CHANGELOG.md` به‌روز، برچسب `vX.Y.Z-rc.N` (اختیاری) |
| ۱. staging | پشتهٔ `deploy/staging` + یک WHMCS آزمایشی | ۱ تا ۳ روز | آزمون‌های E2E سبز، preflight سبز، [چک‌لیست WHMCS](#۷-چکلیست-whmcs-روی-staging) کامل |
| ۲. canary | کنترلر واقعی + **یک** نود + مشتریان داخلی | **۷ روز** | [معیارهای go](#۶-معیارهای-ادامه--توقف-go--no-go) هر روز برقرار |
| ۳. همه | بقیهٔ نودها (دسته‌ای) + همهٔ مشتریان | ۱ تا ۲ روز | preflight سبز، همهٔ نودها روی نسخهٔ بسته، برچسب `vX.Y.Z` |

قواعد کلی:

- هر مرحله با **پشتیبان** شروع می‌شود ([UPGRADE §۰](UPGRADE.md#۰-پیش-از-شروع--پشتیبان-بگیرید)) و با
  **preflight** تمام می‌شود.
- امکانات تازه همه پلن‌محور و پیش‌فرض خاموش‌اند (مثلاً `waiting_room` و `access` در §۱۸)؛ در canary فقط روی
  محصولات/سایت‌های مشتریان داخلی روشن می‌شوند.
- هیچ تغییری بی‌اقدام مشتری روی سایتش اعمال نمی‌شود؛ rollout فقط نرم‌افزار را عوض می‌کند، نه تنظیمات سایت‌ها را.
- برای هر مرحله یک نفر «مسئول rollout» تصمیم ادامه/توقف را ثبت می‌کند (در یک incident داخلی یا یادداشت عملیات).

## ۲. ابزار preflight

`tools/preflight/preflight.py` (فقط کتابخانهٔ استاندارد پایتون ۳؛ نصب لازم ندارد) یک استقرار زنده را
از روی رایانهٔ اپراتور یا خود سرور کنترلر بررسی می‌کند و برای هر مورد `OK` / `WARN` / `FAIL` / `SKIP`
چاپ می‌کند:

| بررسی | منبع | FAIL وقتی | WARN وقتی |
|---|---|---|---|
| `controller /healthz` | `GET /healthz` | پاسخ نیست یا `ok` نیست | — |
| `controller /healthz/deep` | `GET /healthz/deep` | ۵۰۳ / `down` | `degraded` یا هر هشدار |
| `database migrations` | `database.revision` در deep health | revision ≠ head | — |
| `backup age` | `backup` در deep health | پشتیبان موفقی نیست یا قدیمی‌تر از `--backup-max-hours` (۲۶) | پشتیبان‌گیری خودکار خاموش |
| `alert channels` | `alerts` در deep health | — | کانالی تنظیم نشده یا هشدار critical باز |
| `node <name>` | `GET /api/v1/edges` + `GET /edge/version` | heartbeat کهنه‌تر از `--heartbeat-max` (۱۸۰ ثانیه) یا هرگز | نسخهٔ نود ≠ نسخهٔ بسته، `last_error`، پروب سلامت ناموفق |
| `dns <ns> SOA <zone>` | پرس‌وجوی UDP مستقیم به هر `--ns` | بی‌پاسخ، `REFUSED`/`NXDOMAIN`، بدون SOA | پاسخ غیرمرجع (AA=0) |
| `dns serials match` | همان پاسخ‌ها | — | سریال‌ها برابر نیستند |
| `controller TLS` | دست‌دادن TLS با نشانی کنترلر (یا `--tls-host`) | گواهی نامعتبر یا کمتر از ۷ روز | کمتر از ۲۱ روز، یا نشانی کنترلر https نیست |
| `pdns API … closed` | اتصال TCP به ۸۰۸۱ هر `--ns` (یا `--pdns-api`) | **از این رایانه** وصل می‌شود | — |
| `metrics protected` | `GET /metrics` بدون توکن | — | باز است (`METRICS_TOKEN` تنظیم نشده) |
| `alert test` | `POST /api/v1/alerts/test` (فقط با `--alert-test`) | کانالی نیست یا ارسال نشد | بعضی کانال‌ها نرسیدند |

کلید ادمین **فقط** از متغیر محیطی `PCDN_ADMIN_KEY` خوانده می‌شود (هرگز آرگومان خط فرمان) و در خروجی چاپ
نمی‌شود. بدون کلید، بررسی نودها `WARN` می‌شود و زون نمونه را باید با `--zone` داد.

```bash
# از رایانهٔ اپراتور (بیرون از شبکهٔ خصوصی — تا بررسی PowerDNS معنا داشته باشد)
read -rs PCDN_ADMIN_KEY && export PCDN_ADMIN_KEY
python3 tools/preflight/preflight.py \
    --controller https://cdn-api.example.com \
    --ns ns1.pasargadmizban.com --ns ns2.pasargadmizban.com \
    --zone example-customer.ir --strict

# خروجی ماشینی برای پیوست به گزارش rollout
python3 tools/preflight/preflight.py --controller https://cdn-api.example.com --ns ns1.… --ns ns2.… --json > preflight.json

# یک بار در هر مرحله: پیام آزمایشی واقعی به تلگرام/ایمیل (رسیدنش را با چشم تأیید کنید)
python3 tools/preflight/preflight.py --controller https://cdn-api.example.com --alert-test --skip-pdns
```

| کد خروج | معنا |
|---|---|
| `0` | همه OK (یا فقط WARN بدون `--strict`) |
| `1` | دست‌کم یک WARN و `--strict` داده شده |
| `2` | دست‌کم یک FAIL |

نکته‌ها:

- **بررسی PowerDNS** تنها وقتی معتبر است که از بیرون شبکهٔ خصوصی اجرا شود؛ روی خود کنترلر (که حق دارد
  به ۸۰۸۱ وصل شود) `--skip-pdns` بدهید. اگر FAIL شد: `deploy/ns2-firewall.sh` و [DISASTER_RECOVERY §۵](DISASTER_RECOVERY.md).
- اختلاف سریال SOA بلافاصله پس از یک تغییر DNS طبیعی است؛ یک دقیقه بعد دوباره اجرا کنید.
- `--ca-file` برای گواهی‌های CA داخلی (مثلاً staging)، `--tls-host` برای بررسی گواهی عمومی وقتی کنترلر
  را از نشانی داخلی (`http://…:8000`) صدا می‌زنید. همهٔ گزینه‌ها: `preflight.py --help`.
- آزمون‌ها: `python3 -m pytest -q tools/preflight/tests` (کنترلر و DNS ساختگی؛ در CI در کار `ops-tooling`).

## ۳. مرحلهٔ ۱: staging

1. پشتهٔ کامل را بالا بیاورید و آزمون‌های یکپارچه را اجرا کنید ([STAGING.md](STAGING.md#شروع-سریع)):
   ```bash
   deploy/staging/staging.sh up && deploy/staging/staging.sh test
   STAGING_STORAGE=1 deploy/staging/staging.sh up && STAGING_STORAGE=1 deploy/staging/staging.sh test   # اگر Object Storage می‌فروشید
   ```
2. preflight را روی staging اجرا کنید (کلید ثابت staging، فقط یک نیم‌سرور):
   ```bash
   PCDN_ADMIN_KEY=staging-admin-key python3 tools/preflight/preflight.py \
       --controller http://11.200.0.10:8000 --ns 11.200.0.53 --skip-pdns
   ```
   در staging پشتیبان‌گیری خاموش و نشانی کنترلر http است، پس `backup age` و `controller TLS` هشدار می‌دهند؛
   بقیه باید OK باشند.
3. مسیر ارتقای دیتابیس را با دادهٔ واقعی بیازمایید: یک پشتیبان تازهٔ تولید را طبق
   [تمرین DR](DISASTER_RECOVERY.md#۸-تمرین-ماهانهٔ-بازیابی-dr-drill) (`tools/drill/dr-drill.sh`) روی سرور
   آزمایشی بازگردانید؛ کنترلر نسخهٔ جدید باید مهاجرت‌ها را تا head اجرا کند و `manage current` برابر head باشد.
4. ماژول‌های WHMCS نسخهٔ جدید را روی یک **WHMCS آزمایشی** (هم‌نسخهٔ WHMCS تولید؛ `deploy/whmcs-dev` برای
   توسعه) نصب و به کنترلر staging وصل کنید و [چک‌لیست WHMCS](#۷-چکلیست-whmcs-روی-staging) را کامل کنید.
5. (اختیاری، برای نسخه‌های دارای تغییر لبه یا تونل) آزمون بار کوتاه با `tools/loadtest`
   ([LOADTEST.md](LOADTEST.md)) و مقایسه با نسخهٔ قبل.

## ۴. مرحلهٔ ۲: canary (یک نود + مشتریان داخلی، یک هفته)

1. **پشتیبان** کنترلر و WHMCS ([UPGRADE §۰](UPGRADE.md#۰-پیش-از-شروع--پشتیبان-بگیرید))؛ preflight پیش از
   شروع را ذخیره کنید تا مبنای مقایسه باشد.
2. **کنترلر** را طبق [UPGRADE §۱](UPGRADE.md) ارتقا دهید (در HA اول standby، سپس primary). بلافاصله:
   `manage current` = head و preflight بدون FAIL (نودهای قدیمی در این لحظه فقط WARN نسخه دارند).
3. **یک نود** را انتخاب کنید (کم‌بار، در منطقه‌ای که مشتریان داخلی از آن سرویس می‌گیرند) و فقط آن را ارتقا دهید
   ([NODES §۶](NODES.md#۶-بهروزرسانی-یک-نود)):
   ```bash
   curl -fsSL https://<controller>/edge/bootstrap.sh | sudo bash -s -- --upgrade
   ```
   بقیهٔ نودها روی بستهٔ قبلی می‌مانند و در پنل نشان «به‌روزرسانی موجود است» دارند — در این هفته طبیعی است.
   اگر می‌خواهید ترافیک مشتریان داخلی فقط از canary بگذرد، یک گروه نود جدا (مثلاً `canary`) با همین نود بسازید
   و محصول آزمایشی مشتریان داخلی را روی آن گروه بگذارید ([NODES §۳](NODES.md)).
4. **WHMCS تولید** را ارتقا دهید ([UPGRADE §۳](UPGRADE.md)) ولی محصولات/گزینه‌های تازه را فعلاً
   **مخفی** نگه دارید (Hidden در WHMCS) و قابلیت‌های جدید پلن را فقط روی سرویس‌های مشتریان داخلی روشن کنید.
5. هر روز این هفته: preflight با `--strict` (WARN نسخهٔ نودهای قدیمی پذیرفته است و در گزارش ثبت می‌شود)،
   داشبوردهای Grafana و هشدارها ([MONITORING §۶](MONITORING.md#۶-هشدارها-و-مسیر-ارسال))، مقایسهٔ نود canary با
   بقیه، و بازخورد مشتریان داخلی. یک بار در هفته `--alert-test`.

## ۵. مرحلهٔ ۳: همهٔ نودها و مشتریان

1. اگر همهٔ [معیارهای go](#۶-معیارهای-ادامه--توقف-go--no-go) برقرارند، بقیهٔ نودها را **دسته‌ای** ارتقا دهید:
   هر بار حداکثر ۲۵٪ نودهای هر گروه، و پیش از دستهٔ بعد ۳۰ دقیقه صبر و preflight (همهٔ نودهای ارتقایافته OK).
   هرگز همهٔ نودهای یک گروه/منطقه را هم‌زمان ارتقا ندهید.
2. محصولات و گزینه‌های تازهٔ WHMCS را آشکار کنید (Show on Order)، صفحهٔ قیمت‌ها و برنامهٔ معرفی (§18.5) را اگر
   می‌خواهید روشن کنید.
3. preflight نهایی با `--strict` باید کد ۰ بدهد (هیچ نودی با نسخهٔ قدیمی نماند). خروجی `--json` را پیوست
   یادداشت انتشار کنید و برچسب نهایی `vX.Y.Z` را بزنید ([بخش ۹](#۹-نسخهگذاری-و-انتشار)).
4. [چک‌لیست پس از به‌روزرسانی](UPGRADE.md#۴-بعد-از-بهروزرسانی--چکلیست) را روی تولید علامت بزنید.

## ۶. معیارهای ادامه / توقف (go / no-go)

برای رفتن از هر مرحله به مرحلهٔ بعد **همهٔ** موارد زیر لازم است. هر «توقف» یعنی ارتقای بیشتر متوقف و علت بررسی
شود؛ موارد «بازگشت فوری» یعنی [rollback](#۸-بازگشت-rollback-هر-جزء) همان جزء بی‌معطلی.

| معیار | ادامه (go) | توقف | بازگشت فوری |
|---|---|---|---|
| preflight | کد ۰ با `--strict` (WARNهای شناخته‌شدهٔ مرحله ثبت شده) | هر WARN تازه | هر FAIL که با رفع ساده برطرف نشود |
| نرخ خطای 5xx نود canary (لبه، نسبت به کل درخواست) | ≤ میانگین بقیهٔ نودها + ۰٫۵ واحد درصد و < ۱٪ | بالاتر به مدت ۱ ساعت | > ۵٪ به مدت ۱۵ دقیقه (`PcdnErrorRatioHigh` سکو) |
| سلامت نودها | همه آنلاین، پروب سلامت سبز، بدون `last_error` تکرارشونده | `PcdnEdgeOffline` / `PcdnEdgesProbeFailing` برای canary | canary بیش از ۱۰ دقیقه آفلاین یا nginx بالا نمی‌آید |
| کنترلر | `/healthz/deep` = `ok`، مهاجرت‌ها در head، زمان‌بند فعال | `degraded` بیش از ۳۰ دقیقه | ۵۰۳ / خطای مهاجرت / ناخوانا شدن رمزها |
| DNS | ns1 و ns2 مرجع و سریال برابر، `PcdnDnsSyncErrors` صفر | اختلاف سریال بیش از ۱۰ دقیقه | پاسخ نادرست یا NXDOMAIN برای زون مشتری |
| تونل (اگر تغییر کرده) | کیفیت تونل canary هم‌تراز بقیه (صفحهٔ «کیفیت تونل») | افت محسوس قطع/تأخیر | قطع گسترده |
| پشتیبان و DR | پشتیبان موفق < ۲۶ ساعت، `backup-verify` موفق، تمرین DR در ۳۰ روز اخیر | — | — |
| هشدار | کانال تلگرام/ایمیل با `--alert-test` تأیید شده؛ هشدار critical باز نیست | هر critical تازه | — |
| WHMCS | [چک‌لیست بخش ۷](#۷-چکلیست-whmcs-روی-staging) کامل؛ Activity Log بدون خطای تازهٔ ماژول؛ `pcdn_client_errors_total` بدون جهش | خطای تکرارشونده در صورت‌حساب/ساخت سرویس | فاکتور یا کسر اعتبار نادرست |
| مشتریان داخلی | بدون گزارش مشکل باز در هفتهٔ canary | مشکل باز بدون راه‌حل | از دسترس خارج شدن سایت |

## ۷. چک‌لیست WHMCS روی staging

در CI نسخهٔ واقعی WHMCS وجود ندارد؛ همهٔ مواردی که در [WHMCS.md](WHMCS.md) «روی WHMCS آزمایشی بررسی کنید»
آمده‌اند این‌جا یک‌جا شده‌اند. روی WHMCS آزمایشی **هم‌نسخهٔ تولید** بررسی و هر مورد را با نسخهٔ WHMCS و تاریخ
علامت بزنید. اگر موردی رد شد، رفتار جایگزین ماژول (ستون «اگر نبود» در WHMCS.md) را بپذیرید یا انتشار را نگه دارید.

**نصب و ارتقا** ([WHMCS §۱](WHMCS.md#۱-نصب)، [UPGRADE §۳-۴](UPGRADE.md#۳-۴-بررسی))

- [ ] فایل‌های ماژول سرور و افزونه جایگزین شدند؛ با باز کردن صفحهٔ افزونه جدول‌های `mod_pasargadcdn_*` ساخته/به‌روز شدند.
- [ ] [ویزارد «راه‌اندازی خودکار محصولات»](WHMCS.md#ویزارد-راهاندازی-خودکار-محصولات) در حالت به‌روزرسانی بی‌خطا اجرا شد (قالب‌های ایمیل، افزونه‌های ترافیک، گزینه‌های پیکربندی).
- [ ] صفحه‌های «حسابرسی» و «سلامت سامانه» و فهرست نودها در پنل مدیریت باز می‌شوند.

**APIهای WHMCS** ([APIهای WHMCS که باید روی staging بررسی شوند](WHMCS.md#apiهای-whmcs-که-باید-روی-staging-بررسی-شوند))

- [ ] `upgrade.php?type=package&id=…&step=2&pid=…&billingcycle=…` محصول و دوره را از نشانی می‌پذیرد (وگرنه لینک عمومی `upgrade.php?type=package&id=…` کار می‌کند).
- [ ] ارتقای محصول **رایگان** (آزمایشی) به پلن پولی: انتخاب دوره و صدور فاکتور ارتقا.
- [ ] آیا ارتقای سرویس **Suspended** مجاز است (اگر نه، اقدام پایان آزمایشی «توقف روی CDN» بماند).
- [ ] `ShoppingCartValidateCheckout`: `email` / `userid` در `$vars` برای ثبت‌نام هم‌زمان با سفارش هست (پشتیبان: `$_POST['email']`، `$_SESSION['uid']`).

## ۸. بازگشت (rollback) هر جزء

اصل: **کوچک‌ترین جزء ممکن** را برگردانید. ماژول‌های WHMCS طوری نوشته شده‌اند که با کنترلر یک نسخه قدیمی‌تر
کار کنند (امکانات تازه پنهان می‌شوند) و canary فرض می‌کند نودهای نسخهٔ قبل با کنترلر جدید کار می‌کنند؛ این
دو را در staging بیازمایید (یک نود را روی بستهٔ قبلی نگه دارید) تا بازگشت جزء‌به‌جزء امن باشد.

| جزء | نشانهٔ نیاز | روش بازگشت |
|---|---|---|
| **نود لبه** | خطای 5xx، nginx بالا نمی‌آید، تونل قطع | نود را از DNS بیرون بگذارید (در پنل مدیریت نود یا آدرس‌هایش را غیرفعال کنید)؛ سپس روی نود کد نسخهٔ قبل: `cd /opt/pcdn && git checkout vX.Y.(Z-1) && cd edge && sudo ./install.sh --upgrade`؛ پس از سالم شدن دوباره فعال کنید. اگر بستهٔ کنترلر هم برگشته باشد، همان `bootstrap.sh --upgrade` بستهٔ قبلی را نصب می‌کند ([NODES §۶](NODES.md#۶-بهروزرسانی-یک-نود)). |
| **کنترلر (کد)** | خطای API، deep health ۵۰۳ | image/کد نسخهٔ قبل و `docker compose up -d --build` ([UPGRADE §۵](UPGRADE.md#۵-بازگشت-در-صورت-نیاز)). اگر نسخهٔ جدید مهاجرت تازه دارد و کد قبلی با آن کار نمی‌کند، گام بعد. |
| **دیتابیس کنترلر** | مهاجرت نیمه‌کاره یا ناسازگار | اول `manage backup`، سپس `manage downgrade <head قبلی> --yes` (مثلاً `0019`)، سپس کد قبلی ([DR §۹](DISASTER_RECOVERY.md#۹-ارتقا-و-بازگشت-نسخه-rollback-دیتابیس)). ستون‌ها/جدول‌های نسخهٔ جدید حذف می‌شوند (دادهٔ پایه می‌ماند). در صورت خرابی داده: بازگردانی پشتیبان پیش از ارتقا ([DR §۱](DISASTER_RECOVERY.md#۱-بازگردانی-postgresql-از-پشتیبان-رمزنگاریشده)). |
| **PowerDNS / DNS** | پاسخ نادرست | کنترلر نسخهٔ قبل زون‌ها را دوباره می‌نویسد؛ در خرابی نیم‌سرور: [DR §۶](DISASTER_RECOVERY.md). |
| **WHMCS** | خطای ماژول، صورت‌حساب نادرست | پوشه‌های ماژول قبلی (`modules/servers/pasargadcdn`، `modules/addons/pasargadcdn_admin`) را بازگردانید؛ جدول‌های `mod_pasargadcdn_*` بی‌خطر می‌مانند. کران‌های پرداختی (پاداش معرفی، صورت‌حساب ذخیره‌سازی) را تا بررسی در تنظیمات افزونه خاموش کنید. |
| **یک قابلیت** | مشکل فقط در یک امکان تازه | قابلیت پلن را برای سرویس‌های درگیر خاموش کنید (`PATCH /api/v1/sites/{d}/plan` یا گزینهٔ محصول در WHMCS) — بی‌نیاز به بازگشت نرم‌افزار. |
| **CLI / Terraform provider** | انتشار معیوب | انتشار GitHub را «pre-release» یا حذف کنید و نسخهٔ قبلی را توصیه کنید؛ برچسب منتشرشده را بازنویسی نکنید، نسخهٔ وصله بدهید. |

پس از هر بازگشت: preflight، یادداشت در `CHANGELOG.md` (بخش `Unreleased`) و incident داخلی با علت.

## ۹. نسخه‌گذاری و انتشار

- **SemVer:** `MAJOR` برای تغییر ناسازگار API مشتری/قرارداد لبه یا نیاز به اقدام دستی اپراتور، `MINOR` برای
  امکان تازهٔ سازگار (معمولاً هر موج)، `PATCH` برای رفع اشکال. نسخهٔ سکو (کنترلر + بستهٔ لبه + ماژول‌های WHMCS +
  کیت استقرار) یکی است: `vX.Y.Z`.
- **شاخه:** همهٔ کارها با PR به `main` ادغام می‌شوند و CI (`.github/workflows/ci.yml`، از جمله کار
  `ops-tooling` با آزمون‌های preflight و `mkdocs build --strict`) باید سبز باشد. `main` همیشه قابل انتشار است.
- **CHANGELOG:** هر PR تغییر کاربرپسند خود را زیر `## [Unreleased]` در [CHANGELOG.md](../CHANGELOG.md) با
  دسته‌های Keep a Changelog (`Added`، `Changed`، `Security`، `Fixed`، `Removed`، `Deprecated`) می‌نویسد.
- **انتشار:**
  1. `Unreleased` را به `## [X.Y.Z] - YYYY-MM-DD` تبدیل و پیوندهای مقایسه را پایین فایل به‌روز کنید (یک PR).
  2. پس از ادغام، روی همان commit در `main`:
     ```bash
     git tag -a vX.Y.Z -m "Pasargad CDN vX.Y.Z" && git push origin vX.Y.Z
     ```
     برای نسخهٔ نامزد پیش از canary: `vX.Y.Z-rc.N`.
  3. در GitHub یک Release با متن بخش همان نسخه از CHANGELOG و خروجی `--json` preflight نهایی بسازید.
- **CLI و Terraform provider** برچسب‌های جدای خود را دارند و انتشارشان خودکار است
  (`.github/workflows/release.yml` + GoReleaser، امضای GPG): `git tag cli/vA.B.C` و `git tag provider/vA.B.C`
  ([CLI.md](CLI.md)، [TERRAFORM.md](TERRAFORM.md)). اگر تغییری در API مشتری داده‌اید که CLI/provider به آن نیاز
  دارند، آن‌ها را پس از مرحلهٔ ۳ منتشر کنید.
- **مستقرشده = برچسب‌خورده:** روی تولید فقط کد یک برچسب `vX.Y.Z` (یا `-rc` در canary) مستقر کنید
  (`git checkout vX.Y.Z` به‌جای یک شاخهٔ کاری).
