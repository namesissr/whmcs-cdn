# Monitoring stack (Prometheus + Alertmanager + Grafana)

Full guide (Persian): [docs/MONITORING.md](../../docs/MONITORING.md).

```sh
cd deploy/monitoring
cp .env.example .env && chmod 600 .env && $EDITOR .env
docker compose up -d                          # core: /metrics + blackbox probes
docker compose --profile api-bridge up -d     # optional per-edge / traffic / security panels
```

| Path | What |
|---|---|
| `docker-compose.yml` | Prometheus, Alertmanager, Grafana (127.0.0.1 only), blackbox, optional json-exporter |
| `render-config.sh` | renders file_sd targets + `alertmanager.yml` from the environment at container start |
| `prometheus/prometheus.yml` | scrape jobs (`pcdn-controller` with Bearer `METRICS_TOKEN`, probes, bridge) |
| `prometheus/rules/pcdn-alerts.yml` | alert rules; unit tests in `prometheus/tests/` |
| `prometheus/rules/pcdn-slo.yml` | SLO burn-rate alerts (`source="prometheus"`, SPEC §23.11); tests in `prometheus/tests/pcdn-slo.test.yml` |
| `alertmanager/templates/pcdn.tmpl` | Persian Telegram / e-mail messages |
| `json-exporter/config.yml` | admin-API → `pcdn_api_*` mapping (api-bridge profile) |
| `grafana/dashboards/*.json` | generated by `tools/gen_dashboards.py` — do not edit by hand |
| `tools/check_monitoring.py` | CI checks (dashboards, metric names exist, PromQL parses with promtool) |
| `same-host.override.yml` | scrape over the control plane's Docker network instead of HTTPS |

Validate locally:

```sh
python3 deploy/monitoring/tools/check_monitoring.py      # uses promtool from PATH or $PROMTOOL
cd deploy/monitoring && promtool check rules prometheus/rules/*.yml \
  && (cd prometheus && promtool test rules tests/*.test.yml)
```

## SLO alerts: page from ONE source only

The controller computes the SLOs of every edge group (SPEC §23.11, admin page «SLO و بودجهٔ خطا»,
`GET /api/v1/slo`) and exports them on `/metrics` (`pcdn_slo_objective`, `pcdn_slo_ratio`,
`pcdn_slo_error_budget_remaining`, `pcdn_slo_burn_rate`). The same burn conditions can page from two
places — choose one:

| pager | do this |
|---|---|
| **Controller alerts** (default; `slo_burn_fast:<group>:<sli>` critical, `slo_burn_slow:…` warning, `slo_budget_exhausted:…` warning, sent to the controller's Telegram / e-mail alert channels) | do **not** deploy `prometheus/rules/pcdn-slo.yml` (remove it from the rules directory, or route `alertname=~"PcdnSlo.+"` to a null receiver); keep the Grafana dashboard `pcdn-slo` for graphs |
| **Prometheus / Alertmanager** (`PcdnSloBurnFast` critical, `PcdnSloBurnSlow` / `PcdnSloBudgetExhausted` warning, `source="prometheus"`) | keep the rules file and keep `SLO_ENABLED=true` (the controller still produces the metrics); then the controller's own `slo_*` alerts must not page: its alert channels must not be your pager channel (treat them as an informational feed) |

Never both: every burn would page twice. While the controller is unreachable the SLO alerts are
inhibited like the other metric-derived alerts (`render-config.sh`). Dashboard: `grafana/dashboards/pcdn-slo.json`.
